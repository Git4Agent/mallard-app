# Mallard Frontend Re-audit

**Scope:** `src/` (48,539 lines of `.ts`/`.tsx`/`.css`), `tests/frontend/`,
`scripts/run-frontend-integration-tests.mjs`, `index.html`, `vite.config.ts`,
`public/`, and the Tauri seam where it meets the frontend (`tauri.conf.json`,
`capabilities/`, the `invoke` boundary, DTO contracts).
**Audited at:** `d78e3c5` *Add shared loading scaffolds*. **Date:** 2026-08-25.
**Nature:** audit only — no source file was modified.
**Predecessor:** `frontend-audit-findings.md` (2026-08-21, findings F1–F72).

**Method.** Twelve auditors swept one dimension each; every dimension's findings
were then handed to an adversarial verifier instructed to refute them, defaulting
to REFUTED when the failure path could not be traced in real code. A completeness
critic then looked for what the twelve structurally could not see. 71 raw findings →
**68 survived** → **55 after de-duplicating** the same defect reported by several
dimensions. All seven findings the sweep rated high were then re-verified by hand against
source — including the `tauri` 2.11.3 and `muda` 0.19.3 crate sources and the Rust
`Debug` derivation behind an error string. One was demoted to medium on that
review (R14), leaving six.

**Confidence.** `CONFIRMED` = the failing path was traced end to end in real code.
`PLAUSIBLE` = the code is wrong but the trigger depends on runtime state that could
not be exercised by reading.

---

## Verdict

The frontend is in materially better shape than at the 21 August audit. The three
findings classes that dominated that report are now **empty**:

- **The IPC surface is exactly closed.** 78 `#[tauri::command]` functions defined,
  78 registered in `generate_handler!`, 78 distinct names invoked from `src/` —
  all three sets equal. F38's deferred cleanup was completed: `get_bundle_status`
  and `get_bundle_readiness` no longer exist anywhere, and the Catalog rewrite
  deleted 8 more commands without stranding one.
- **DTO drift is zero.** All 138 exported types in `src/types.ts` and 40 in
  `storage-catalog/types.ts` were diffed field-by-field against every `pub struct`
  and `pub enum` in `src-tauri/` and `crates/`: no shape mismatch, and no case of
  "TS required where Rust may omit" — the class that renders `undefined`.
- **The CSS orphan count is 0** against a ratchet that expects 0, and cross-file
  shadowed pairs are 403 against a 423 ratchet.

What replaced them is a different and more interesting failure mode. **Seven of the
fifty-five findings are regressions of fixes the last audit implemented** (F16, F25,
F29, F58, F59, F60, F72), and three more re-commit a prior mistake in new code
(R36, R42, R51 — a fix applied to one of two copies). The shapes recur: a tone
parameter dropped by a one-argument arrow, a menu-focus helper imported without the
half that restores focus, a test fixture pinning a string the backend cannot emit.
In every case the gate meant to protect the fix still passes, because it asserts
source text rather than behaviour.

That is the through-line: **the suite's 2,017 assertions include 834 (41%) that
read source text with `readFileSync`, and only 683 (34%) that inspect rendered
output.** A source-text assertion cannot tell a wired callback from an unwired one.
Wave 2 of the previous audit — the behavioural safety net — was never built, and
the cost of not building it is now measurable in the list below rather than
theoretical.

### Root causes

**A — Gates that assert text, not behaviour.** R05, R08, R14, R28, R34 and R36 all
survive a green suite. R05 is the sharpest: the only test covering
`isIrrecoverableSyncError` feeds it a hand-written string, and the two rules it
certifies match nothing the backend can produce.

**B — A newly shipped feature whose geometry does not match the pages it stands
in for.** `d78e3c5` landed loading scaffolds specifically to stop layout shift on
arrival. Measured by computed style, the `rows` scaffold copies the App.css values
that RetroTheme.css overrides, and the `detail` scaffold draws a two-column pane
block and a page-wide tile band that session detail never renders. Both produce
the reflow they exist to prevent (R02, R03).

**C — Quit is not close.** The window close guard added as F35 listens on
`onCloseRequested`. ⌘Q reaches `NSApplication terminate:` and never raises it (R04).

**D — One escaped boundary.** `storage-catalog/` now imports a `project-sync/`
component, the first such import in the directory, and nothing in the suite gates
it (R28, R34).

**E — Formatter churn re-committed in new code.** F25's per-row `Intl` mistake was
fixed on the Activity page and then re-made in the rewritten Catalog row: ~10
`DateTimeFormat` constructions per row per render, 12.7 ms per render at this
machine's real 41 rows (R29).

## Remediation order

**Wave 1 — inert fixes and live breakage (R01–R06, R14).** Small, mechanical, and
each one restores something the last audit already paid for. R04 (⌘Q) and R05
(dead irrecoverable-error rules) are the two with data-integrity consequences.

### R04 — ⌘Q and the Quit menu item kill a running Push/Pull without the close guard ever running

`src/components/project-sync/ProjectSync.tsx:1191` · CONFIRMED · dimensions: shell

**What it is.** The F35 guard is registered as a window close-requested listener: ``` 1191: useEffect(() => { 1192: if (!busy) return; 1194: const pending = getCurrentWindow().onCloseRequested(async (event) => { 1195: if (!busyRef.current) return; 1196: event.preventDefault(); 1197: const leave = await confirm("A sync is still writing. ..."); 1201: if (leave) await getCurrentWindow().destroy(); ``` That only ever fires for `WindowEvent::CloseRequested`. I traced where that event can come from: - `tao-0.35.3/src/platform_impl/macos/window_delegate.rs:326-330` — `WindowEvent::CloseRequested` is emitted from **one** place, `window_should_close` (macOS `windowShouldClose:`). That selector is called for the red traffic-light button and for `performClose:` (⌘W), and for nothing else. - `tao-0.35.3/src/platform_impl/macos/app_delegate.rs:59-83` registers `applicationDidFinishLaunching:`, `applicationWillTerminate:`, `application:openURLs:` … and **no `applicationShouldTerminate:`**. `NSApplication terminate:` therefore proceeds straight to exit; no window is asked. - The app installs no menu and no window-event handler: `grep -rn "menu|Menu" src-tauri/src/lib.rs` and `grep -rn "on_window_event|RunEvent" src-tauri/src/*.rs` are both empty, so Tauri's `Menu::default` is used (`tauri-2.11.5/src/menu/menu.rs:178-195`), whose macOS app submenu ends in `&PredefinedMenuItem::quit(app_handle, None)?`. - `muda-0.19.3/src/items/predefined.rs:339` gives that item the accelerator `Accelerator::new(Some(CMD_OR_CTRL), Code::KeyQ)`, and `muda-0.19.3/src/platform_impl/macos/mod.rs:994` wires it to `PredefinedMenuItemType::Quit => Some(sel!(terminate:))`. So ⌘Q → `terminate:` → process exit, with no `windowShouldClose:`, no `CloseRequested`, and no chance for the JS handler at 1194 to run.

**What breaks.** Start a Pull that has 400 MB of objects to fetch and apply (the review footer states "A running pull finishes or fails whole — it can't be cancelled midway"). Mid-apply, press ⌘Q — or choose Mallard ▸ Quit Mallard. The process terminates instantly: no "Sync in progress" dialog, no chance to keep syncing. The bundle write and the local journal entry are left half-committed, which is precisely the outcome F35 was implemented to prevent. The same gesture on the red close button, two inches away, does show the confirm — so the guard reads as shipped and complete while the most common macOS quit gesture walks straight past it.

**Plan.** Fix in `src-tauri/src/lib.rs`, not in the frontend — the frontend listener is correct, it is simply never reached. 1. Build the menu explicitly instead of taking `Menu::default`: keep every predefined item, but replace `PredefinedMenuItem::quit(app, None)` with `MenuItem::with_id(app, "quit", "Quit Mallard", true, Some("CmdOrCtrl+Q"))`. 2. Add `.on_menu_event(|app, event| { if event.id() == "quit" { if let Some(w) = app.get_webview_window("main") { let _ = w.close(); } } })`. `Window::close()` (`tauri-2.11.5/src/window/mod.rs:1794`) routes through the runtime's close path and emits `CloseRequested` — the doc on the neighbouring `destroy()` at :1798 says exactly that ("Similar to `Self::close` but does not emit any events"). When nothing is in flight there is no JS listener, `manager/window.rs:171` does not call `prevent_close()`, and the window closes as it does today. 3. Leave `PredefinedMenuItem::close_window` (⌘W) alone — it goes through `performClose:` → `windowShouldClose:` and is already covered. 4. Prove it: `npm run tauri dev`, point a project at a large local storage, start a Pull, press ⌘Q while the apply is running. Expect the "Sync in progress" dialog; "Keep syncing" must leave the window up and the pull running, "Quit anyway" must exit. Repeat with no sync running and confirm ⌘Q still quits in one keystroke.

**Correction from the verifier.** Two corrections, neither fatal. (a) Version drift: Cargo.lock pins tauri/tauri-runtime-wry 2.11.3, not 2.11.5 (both trees happen to be in the registry cache). The cited facts hold identically in 2.11.3 — Menu::default's quit item is at tauri-2.11.3/src/menu/menu.rs:201, the install site at app.rs:2244-2249, `Window::close` at window/mod.rs:1794 with the same doc line, `destroy` at :1799. Re-verify against 2.11.3 when implementing. (b) Severity: this is the same risk class as F35 itself, which the prior audit rated MEDIUM/PLAUSIBLE, and the trigger requires the user to quit during the write window — medium is the better rating than high. One useful addition to the fix plan: the proposed `w.close()` from inside `on_menu_event` is safe even though tauri-runtime-wry lib.rs:3491 panics on `WindowMessage::Close` — `Dispatcher::close` at lib.rs:2277-2281 uses `proxy.send_event` directly rather than `send_user_message`, so the message lands at lib.rs:4368 → `on_close_requested`, not on the panicking main-thread path. Worth stating in the plan so the implementer does not shy off it.

### R05 — The only test covering isIrrecoverableSyncError asserts a hand-written message the backend cannot produce, certifying two dead rules

`tests/frontend/pull-review.integration.test.tsx:411` · CONFIRMED · regression of **F16** · dimensions: tests

**What it is.** The test fixture is a literal invented in the test file: ```ts const message = "conversation Pull action 'action-a' is stale at SemanticDigest"; ... assert.equal(isIrrecoverableSyncError(message), true); ``` The real producer is `src-tauri/src/project_sync/commands.rs:9899` / `:10990`: ```rust format!("conversation Push action '{}' is stale at {:?}", action.action_id, pin) ``` where `pin: ConversationStalePin` is `Tail(ConversationTailPin::SemanticDigest)` — `crates/mallard-infrastructure/src/conversation_sync.rs:202` returns `Err(ConversationStalePin::Tail(Tail::SemanticDigest))`, and line 199 returns `Tail(Tail::LineageDigest)`. Both enums use `#[derive(Debug)]` with no manual impl (grep for `impl.*Debug for ConversationStalePin` → nothing). I compiled the exact shape with rustc to remove all doubt; it prints: `conversation Push action 'action-a' is stale at Tail(SemanticDigest)` The frontend rule at `src/components/project-sync/syncError.ts:9-10` is `normalized.includes("stale at semanticdigest")` / `"stale at lineagedigest"`. Lowercased, the real message reads `...is stale at tail(semanticdigest)` — the interposed `tail(` means neither substring can ever match. The message reaches the check unmodified: `commands.rs` pushes it into `stale_conversations` → `failed_actions[].message` → `syncOutcome.ts:249-250` `[error, ...failures.map(f => f.message)].some(isIrrecoverableSyncError)`; the only transform on the path, `userFacingRepoTerms` (`src/terminology.ts:9`), rewrites only the word "Bundle".

**What breaks.** A user edits a conversation locally between building a Pull plan and applying it, so the semantic digest moves. The backend rejects with `conversation Pull action 'a-1' is stale at Tail(SemanticDigest)`. `isIrrecoverableSyncError` returns false, so `syncOutcome` offers **Retry** instead of "Reset local sync state" (`RestorePlanView.tsx:421`, `PushResourceWorkspace.tsx:708`, `ProjectLinksWorkspace.tsx:2435`). Retry rebuilds a plan against the same contradictory durable metadata and fails identically — an endless Retry loop with no route to the one control that fixes it. The suite stays green because the test hands the function a string the backend never emits. Note this also corrects prior finding F16, which recorded `isIrrecoverableSyncError` as having 'zero tests': the test exists (it predates the audit, added in d2957b8) and is worse than none, because it certifies the broken rule.
