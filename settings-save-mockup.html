Recommendation · B, top

B at the top answers both needs, and it adds no button that claims to save. Changes already reach disk as you make them (tens of ms), so a Save button would be clicked after the work is done. Every platform guide below says settings should apply immediately. What they add is visible feedback (NN/g, Pajamas, Primer) and a clear way to finish.

Why top rather than bottom: the path bar stays visible however far down the page you are (seven groups), and it's already where the page's verbs go. The bottom tile costs about 60px of height on every visit, and it puts a button exactly where people look for Save, which brings back the "did I need to press that?" doubt. Bottom's one advantage: it's where forms end. C is the honest version if you really want a Save button (see its costs below).

What the standards say

  • Microsoft, Guidelines for app settings: a changed setting should take effect immediately, with no confirmation button. Settings is the last item of the navigation pane, which is where Mallard already puts it.
  • NN/g, Don't Prioritize Efficiency Over Expectations: people assume nothing changes until they press Save. If you autosave, show "Saved" beside each field as it changes, so they know nothing else is needed. (Their example: Nextdoor's email settings.)
  • GitHub Primer, Saving and ToggleSwitch: switches, segmented controls and single-select menus save instantly. Don't mix save models in one form, use one Save button per page, and confirm autosaves with an inline message rather than a toast. A switch is an instant-save control; checkboxes are for forms with Save.
  • GitLab Pajamas, Saving and feedback: autosave each input on its own, show "Saving…" then "Change saved" / "x changes saved" inline, show failures as an inline alert with retry, and use one model per page.
  • Shopify, contextual save bar (now the App Bridge Save Bar): it appears only while a form has unsaved changes, reads "Unsaved changes" with Discard and Save, and asks before you leave. That's direction C.
  • Apple, HIG · Settings: the macOS section covers the settings window (toolbar, title, ⌘,) and gives no rule about when changes apply. macOS System Settings itself has no Save button.

One conflict to settle: Primer counts native <select> as an explicit-save control, and Mallard's Performance and Logs selects apply on change. Pajamas autosaves every input, selects included, and the rule both systems actually enforce is one model per page. So the selects stay instant (or become single-select menus); switching only them to Save would create the mixed page both guides warn against.

What any pick has to deal with

  • The receipt has to be true first. preferences.ts writeKey swallows its storage error, so a "Saved" on Theme, Open Logs, Refresh on focus or 24-hour clock would show no matter what. It has to report success, and setPreference/setThemeChoice have to pass that on.
  • Where Done lands. openSettings runs closeWorkspaceSettings() on the way in, which resets the project to its overview and closes Storages, Catalog and storage pages. So Done lands on the open project's overview, or on Projects if none is open. Returning to the exact previous page would need a remembered return target (new state). The button's tooltip names the destination.
  • It's the app's first Back/Done control. Everywhere else the path-bar trail is the way out, but Settings has no parent crumb. Esc → Done is the natural keyboard pair, but only when no menu or dialog is open, since Esc already closes path-bar menus and popovers.
  • New text in the bar needs data-tauri-drag-region. The path bar is the window's titlebar, and every non-interactive child carries the attribute. B · top's status (and C · top's "N unsaved changes") without it is a strip where the window can't be dragged, which is how this bar broke once before. The footer tile isn't the titlebar.
  • Not the notice under the bar. That slot never dismisses itself (it has a Dismiss button), and a banner per toggle would be noise.
  • Contrast is measured, not assumed. On the composited surfaces they print on, at the status's 11px: the lowest is success on the light bar tile at 5.25:1; danger is 5.49 and text-2 is 5.41; in dark everything is at least 6.5. All clear AA 4.5:1.
  • One polite role="status" region announces every receipt (for example "Push Codex children saved"). The row stamps are aria-hidden, and failures keep the section's existing alert.
  • Performance knobs also drop cached comparisons (tuning_differs → reset_all_caches_and_purge_disk), so the next refresh starts cold. "Saved" is still true. Should it say more? My default is no.
  • While a write is in flight, today's switch shows its old value until the read-back lands, because it's controlled by tuning. You never see this at real speeds, but if "Saving…" ever shows, the control should show the value being written.
