B, settled · what the form does now

The form is kept because it is the shape people already learned during setup; what changes is that nothing on it is a place to type except the name. Four decisions fill in the rest:

  • Fixed fields are readonly, not disabled. Readonly text keeps full contrast, takes focus, and selects (⌘A in the field, or triple-click), so a value can be copied without a Copy button. A lock beside the field's name says why it doesn't type; the footer says it once in words: destination and credentials are fixed, another bucket is a new storage.
  • Show fetches, it doesn't unmask. The secret is not in the page: the field holds a mask, and Show asks the backend for that one value (reveal_storage_secret). It is shown in the field, Hide or the timer drops it, leaving the page drops it. Copy works without Show: it fetches, puts the value on the clipboard, and drops it, with a "Copied" receipt. Both R2's Secret Access Key and Dropbox's two tokens behave the same way; Dropbox's access token says it renews automatically so nobody tries to keep it.
  • Hides after 30 s by default. Password managers auto-conceal (1Password, Bitwarden); consoles (AWS Secrets Manager, Stripe) leave it until you navigate. The countdown sits in the label row, so the hide never surprises. "Until you leave" is on the toggle if you'd rather.
  • The name saves itself. It is the one live field, so it follows the Settings page's receipt grammar (2026-09-11): save on blur or Enter through the existing rename_storage, "Saving…" → "Saved" beside the field, Esc restores, and a refused name ("already used by another storage") stays in the field with the reason. No Save button, so no button that claims to save the locked fields too. The shipped ⋯ → Rename row is on the toggle as the fallback.

Refused credential keeps A's answer: the secret's label wears a Refused chip and the guide row's Reconnect… opens the one editable band (R2: paste, Test, Save credential; Dropbox: the shipped sign-in lane; Local: Browse…). The locked fields stay locked underneath it — same bucket, same account, new key.

What the standards say · revealing a saved secret

  • AWS Secrets Manager console: a secret's page shows its metadata; the value appears only after Retrieve secret value, a separate call that is recorded (CloudTrail). Reveal is an explicit act, fetched on demand, logged. Mallard's version: reveal_storage_secret on Show, one event in the Logs drawer, never the value.
  • 1Password and Bitwarden: concealed fields with a per-field reveal and a Copy that works without revealing; values conceal again on their own (1Password auto-conceal, Bitwarden hides on navigation and clears the clipboard after a timeout). That is the Show + Copy + 30 s pattern.
  • Stripe, API keys: test secret keys can be revealed in the dashboard; live keys are shown once and then only rolled. Cloudflare R2 shows a token's Secret Access Key once, at creation; GitHub PATs likewise. That is the case for Mallard revealing at all: for R2 it is the only place the user can still read the key they saved.
  • Apple HIG, Text fields: a secure field hides its content; give people a way to show it when they need to check it. macOS Keychain Access does the same with a "Show password" checkbox, gated by the login password — Mallard has no such gate, so the timer and the log do the reassuring instead.
  • Material 3, Text fields: a password field's trailing icon toggles visibility; read-only fields inside a form must look distinct from editable ones. The lock glyph and the muted surface (--surface-muted) do that here, with the name field the one raised surface.
  • NN/g, Stop password masking and the show-password follow-ups: masking without an unmask control is what causes errors and re-typing; a visible toggle costs nothing when the person is alone at their machine.
  • WCAG 2.2, 1.4.3: inactive controls are exempt from contrast, which is exactly why the fixed fields are readonly and not disabled — readonly text keeps its normal ink and stays selectable.

Project fit · the plan

What the page reads

  • No edit draft for viewing. Today opening settings runs create_storage_edit_draft and autosaves a draft that shadows the storage (the index then says "Unsaved settings — not applied yet"). B needs only the storage's settings and secret presence: one new read, get_storage_details(storage_id) → { settings, secrets: [{secret_id, present}] } (the StorageSetupDraftSummary shape minus the draft fields), or the same two fields added to StorageSummary. No draft file, no revision, no autosave, no discard.
  • Reveal is its own command. reveal_storage_secret(storage_id, secret_id) → String, declared secrets only (as the exact-fetch of a new draft already filters), reading the committed provider_config.secrets. This deliberately reverses the rule in secrets.rs ("a saved value is never returned to the frontend") for one explicit, per-secret call; the listing, drafts and updates stay redacted. The Rust side zeroizes on drop as it does now; the JS side holds the value only in the field's state while shown and drops it on Hide, timer, or unmount. Record one Logs event ("Secret revealed · · "), never the value.
  • Copy calls the same command and writes to the clipboard without setting the field visible; the 1.5 s "Copied" receipt reuses the Settings stamp classes.

What the page writes

  • Name: the existing rename_storage(storage_id, name, expected_config_revision) on blur/Enter, trimmed, skipped when unchanged; the receipt hook from settingsReceipts.ts drives Saving…/Saved/failed. A refused rename keeps the typed name and shows the backend's reason; Esc restores the saved one.
  • Test connection: needs test_storage(storage_id) on the committed config (today only drafts can be tested) and it should refresh connection so the guide row's "verified N min ago" is a real observation.
  • Reconnect stays on a draft — the only place a draft is still created for an existing storage — with the backend refusing any settings change on an edits_existing draft (immutability enforced by the API, not only the UI). Dropbox's shipped lane already works like this; R2's band is the secret field + Test + Save credential.

Removed (clean cutover)

  • Edit-draft autosave, saveStorageDraftBeforeNavigation on the storage page, "Discard draft", the index's "Unsaved settings" caption, and saveEditedStorage / Save storage.
  • immutable_on_edit on StorageFieldDescriptor (only Dropbox set it; under B every field is immutable on edit), in the types and the three adapters.
  • The disabled type switch on an existing storage; onSwitchProvider stays for new drafts only.
  • The "Stored — type to replace" placeholder and the typed-secret path (typedSecrets, secretOperationsFromForm) for existing storages — they remain for creation and for the reconnect band.
