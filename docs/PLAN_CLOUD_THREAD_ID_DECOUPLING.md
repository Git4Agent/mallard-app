# Cloud thread id decoupling

Status: **Implemented** (2026-08-19; planned and revised the same day — all identity minting moved from planning to apply). Compatibility: clean cutover — no migration, no legacy execution path, no schema-version bumps (the cloud bundle schema is unchanged on the wire; local documents reshape in place and fail closed). `~/.mallard` and all cloud data are wiped before retesting; there are no customers.

Implementation notes (deltas from the stages below, discovered while landing):
- Three machine-local recipe filters detected conversation resources with the **local-space** parser (`machine_local_recipe_from_manifest`, `preserve_unchanged_scope_recipe_revision`, `BundleRecipe::validate_machine_local`); with manifest resources now cloud-space they silently passed. Fixed with a space-agnostic `is_conversation_resource_id` (either namespace) — caught by existing tests.
- `ConversationApplyReceipt` gained `preserved_display_title` so `PreservedThreadResult` reads the minted marker title from the journal-sourced receipt (the plan's "reads from the journal, never from a plan" needed a carrier field).
- The push-mint conflict arms covered by tests are the mapping cross-checks (action/row mismatch both directions); the minted-id collision arms (previous manifest / binding claim / batch) are structurally untestable without controlling randomness — a 96-bit random id cannot be pre-seeded — and stay guarded by the fail-closed membership check itself plus batch-duplicate detection. The mapped-`CreateCloud` reuse arm (second storage / post-remote-deletion republish under the existing `t_c`) shares the resolved-`Some` code path with every mapped Publish the live suites exercise, but has no dedicated multi-storage test.
- `mint_provider_thread_id` stayed in place (commands.rs) and is now called only from `apply_prepared_pull_conversation`; the review-side occupied set and the discovery-inventory input were deleted with it (apply's occupied set = prepare capture views ∪ binding provider ids ∪ batch).

## Context

Today one `ThreadId` value is shared between a conversation's local registration and its cloud record. The coupling has exactly two production sources:

1. **First contact derives the id from the provider session id.** An unbound local session gets `initial_conversation_thread_id(bundle_id, provider, provider_thread_id)` (lib.rs:3617, used at commands.rs:5399), and Push publishes the cloud row under that same value (`result_thread_id = action.thread_id`, commands.rs:8853). The cloud id is therefore a pure function of the first pusher's local session id.
2. **Pull adopts the cloud id as the local registration key.** CreateLocal and keep-both's tracking row are created with `thread_id = action.thread_id` — the cloud row's id (commands.rs:11287, 11319) — and checkpoints key the same value (11375); MaterializeCloud updates a row that already carries the adopted key from an earlier pull or push.

The provider-native layer is **already decoupled** and stays untouched: pull always mints fresh provider session ids for Codex (copy-on-write MaterializeCloud, KeepBoth, CreateLocal — commands.rs:6327/6389/6492 via `mint_provider_thread_id`) and for Claude CreateLocal (uuid v4); pulled content is reidentified to the minted id (Codex `StandaloneBuildMode::Decode`, commands.rs:10928-10937; other providers `adapter.rewrite`, commands.rs:10963-10969, which rewrites the in-content `sessionId`/`cwd`). This feature completes the same decoupling one layer up, at the Mallard `ThreadId`.

**Target model (user decisions):**

- When machine A pushes local thread `t_a`, the cloud stores it under an independently minted id `t_c`. `t_c` never equals any machine's local id.
- When machine B pulls `t_c`, it mints a new local thread `t_b` and copies the content into it — the mechanics divergent pull already uses, now the rule for every first materialization at the ThreadId layer too.
- Each machine keeps the pairing in `~/.mallard`: A stores `(t_a, t_c)`, B stores `(t_b, t_c)`. The cloud stores **no** mapping and no local identity with linkage semantics.
- **All fresh identities are minted at apply, never at planning.** Any conflict at apply fails the operation — no retry, no reconciliation. Minted identities are saved locally as documents (journaled operation + whole-document after-states → the `~/.mallard` bindings/config documents).

## Decisions

**D1 — Two id spaces, structurally disjoint, enforced by distinct domain types.**
- *Local thread id* (`t_a`, `t_b`) — the existing `ThreadId`, namespace `thread-…` (derived 32-hex, generated 24-hex): keys bindings, checkpoints, journal-op `thread_id`, receipts, Activity. Never serialized into a bundle. `ThreadId::parse` additionally **rejects the `cloudthread-` prefix**, so no cloud value can ever parse as local.
- *Cloud thread id* (`t_c`) — a **new domain type `CloudThreadId`**, namespace `cloudthread-…`, minted via `generated_named_id("cloudthread")`; its parse pins the prefix. Keys manifest rows, cloud resource ids, logical paths, tombstones, and provenance references. Manifest validation rejects any conversation row outside this namespace, so a manifest — external input — **cannot inject a local-space id at all**.
- Typed fields: `ConversationThread.thread_id`/`forked_from`, `PreservedProvenance.preserved_from`, `TombstoneTarget::ConversationThread`, scope `conversations` map keys, `LocalConversationBinding.cloud_thread_id`/`forked_from`, plan-action `cloud_thread_id`, op `cloud_thread_id`, DTO `ThreadSyncEntry.cloud_thread_id`. Cross-space comparison becomes a **compile error**, retiring the "missed id-equality join" bug class for every typed field.
- Row-key strings are disjoint by construction — `<provider>:conversation:thread-…` vs `<provider>:conversation:cloudthread-…` — so the frontend resource-id `Map` join, the Activity merge fold, and the deep-link guards can never collapse rows from different spaces, even for deliberately colliding manifests. `parse_conversation_resource_id` (local) rejects cloud-space resource ids automatically via `ThreadId::parse`; manifest validation gets a cloud-space parser.
- *Review finding this replaces:* the first draft kept one `ThreadId` type and claimed the spaces were "structurally distinguishable in practice" — false (KeepBoth's preserved **local** ids are 24-hex `thread-` values too, and `named_id!` pins no prefix at all, lib.rs:65-75/141), and unsafe (equal strings across spaces would share one row key and one journal-blocking namespace).

**D2 — Every fresh identity is minted at apply, never at planning; any conflict fails the operation.** Plans are pure intent: review classifies relations and pins evidence, but assigns no new identity of any kind — no cloud thread id, no local thread id, no provider session id, no keep-both preserved identity or marker title. Minting happens at apply, immediately before the operation and its whole-document after-states are constructed and journaled, so **recovery never mints** — crash replay installs the journaled documents verbatim.
- *Push (`CreateCloud`, unmapped thread):* `build_publish_request` mints `t_c = CloudThreadId::parse(generated_named_id("cloudthread")?)`. Single attempt, fail-closed: a minted id already among the previous (CAS-pinned) manifest's `all_conversations()` ids, claimed by any binding row's `cloud_thread_id`, or repeated within the batch is a hard error — no retry loop. A mapped thread always publishes under its existing `t_c` — including `CreateCloud` toward a second storage or after a remote deletion — so one thread keeps **one portable identity across all storages**. The build re-checks the live row defensively: reviewed-as-unmapped but now mapped, or mapped to a different id than the action carries, is a hard error, never a silent adoption.
- *Pull (`CreateLocal`, codex-relocate `MaterializeCloud`, `KeepBoth`):* `apply_prepared_pull_conversation` mints the destination provider session id (codex allocator / uuid v4, against an apply-time occupied set: the prepare capture's session views ∪ binding rows' provider ids ∪ ids minted earlier in the batch — exhaustion fails), assigns `t_b = initial_conversation_thread_id(bundle, provider, p_b)` for CreateLocal, and for KeepBoth mints the preserved ThreadId and composes the provenance ordinal + marker title. Adapter targets are computed at apply under the minted id, and **every minted-identity target must be Absent — an occupied path fails that action** (per-action failure receipt, the existing pattern); the engine's no-clobber commit backstops it, and the codex index writer's collision arm ("reserved Codex provider ID is already indexed", commands.rs:10771-10778) is another conflict→fail.
- Racing operations are serialized by the existing `bindings_document_revision`/`binding_revision` pins (and the host-operation lock locally): the loser goes stale and replans against committed state — a replanned CreateCloud then carries `Some(t_c)` from the committed mapping.
- **Journal insertion is the identity-uniqueness gate.** `insert_operations` (conversation_materialization.rs:1047-1082) extends its pending-op uniqueness from `(local_project_id, provider, thread_id)` to also reject a matching `(local_project_id, cloud_thread_id)` — deliberately *not* provider-qualified, cloud ids are bundle-global — and a duplicate non-null `(plan_id, plan_action_id)`; `ConversationSyncJournal` document validation enforces the same three invariants. This closes the interrupted-CreateLocal retry hole that apply-time minting opens: attempt 1 mints `p_b1`/`t_b1` and journals at TargetStaged, then crashes before the binding commit — the bindings revision is unchanged, so the saved plan's pins still pass — and attempt 2 mints fresh `p_b2`/`t_b2`, which the old local-id-only guard would wave through; the shared `cloud_thread_id` (and the same plan action) rejects the second insertion, so no second identity is ever journaled. Apply also pre-checks the journal by cloud id **before** minting or staging (ergonomics; the insertion-time check under the host-operation lock stays authoritative). Push retries were already safe: a re-pushed CreateCloud keeps its stable local `thread_id` (caught by the existing guard) and the head CAS rejects a republish after a crashed head advance.
- **Minted identities are saved locally as documents.** Before any visible mutation, every minted value is journaled inside the operation (`thread_id`, `cloud_thread_id`, `provider_thread_id`, `KeepBothJournal`) and inside its `bindings_after`/`sync_config_after` whole-document snapshots; commit installs them into `~/.mallard`'s bindings/config documents. Recovery and receipts read minted identities from the journal — never from a plan, never by re-derivation.
- Side benefit: reviews become idempotent — repeated reviews of unchanged state produce identical plans modulo `action_id`/`expires_at`.
- *Superseded precedent:* the "identities are minted during planning; apply and recovery never mint" rule (lib.rs:3151-3155, and PLAN_PRESERVED_THREAD_PROVENANCE's plan-time marker composition) is replaced wholesale — user decision. Its load-bearing half, **recovery never mints**, is preserved unchanged.

**D3 — The mapping lives on the binding row: `LocalConversationBinding.cloud_thread_id: Option<CloudThreadId>`.** Machine-global, exactly like the row itself. `None` = local-only thread (never published, or deliberately detached by keep-both). Validation in `ConversationBindings::validate_structure` (lib.rs:1973-2016): per `(host_id, replica_id, local_project_id, provider_profile_id)` scope, at most one row may claim a given `cloud_thread_id`.
*Rejected:* per-storage mapping (e.g. inside checkpoints) — it would mint a different `t_c` per storage for one thread, so a machine pulling two storages of one bundle would materialize duplicate local threads.

**D4 — Local id assignment rules (uniform, pinned at registration, never re-derived):**
- Discovered unbound local session → `initial_conversation_thread_id(bundle, provider, session_id)` — unchanged (commands.rs:5399). Its documented purpose ("stable before the first publication commits a binding") becomes its *only* purpose; it no longer determines any cloud identity.
- Pull-created rows (`CreateLocal`) → `initial_conversation_thread_id(bundle, provider, p_b)` where `p_b` is minted at apply (D2). The plan carries neither id. The derivation keeps one uniform rule ("first identity = derivation of the first provider alias"), and an orphaned materialized file whose binding is lost re-derives the same id at rediscovery.
- Retained displaced rollouts → `retained_conversation_thread_id` — unchanged (local ids in, local ids out).
- KeepBoth preserved copy → `generated_named_id("thread")`, minted at apply — value rule unchanged, timing moved.
- Provider-alias moves (codex copy-on-write) never change a row's `thread_id` — unchanged.

**D5 — Plans carry intent; journal ops carry the complete identity record.**

| Action | `thread_id` (local) | `cloud_thread_id` |
|---|---|---|
| Publish | `Some` | `Some` (mapping) |
| CreateCloud | `Some` | `Some` (mapping) / `None` (unmapped → mint at apply) |
| AdoptCloudMetadata | `Some` | `Some` (reviewed cloud row) |
| MaterializeCloud | `Some` | `Some` (reviewed cloud row) |
| KeepBoth | `Some` | `Some` (reviewed cloud row) |
| CreateLocal | `None` (minted at apply) | `Some` (reviewed cloud row) |

- `ConversationPlanAction.thread_id` becomes `Option<ThreadId>` and `cloud_thread_id` is `Option<CloudThreadId>`; the presence matrix above is validated per action type; both-`None` is impossible, so every action names at least one id. Push-plan validation additionally requires `Some(thread_id)` on its Publish/CreateCloud actions.
- `proposed_provider_thread_id` and `keep_both: Option<KeepBothPlan>` are **deleted from the plan action**, and `KeepBothPlan` dies as a domain type — those identities do not exist at plan time. `KeepBothJournal` (op-level, minted at apply) survives and gains `preserved: PreservedProvenance` + `preserved_display_title: String`, so receipts and `PreservedThreadResult` read minted keep-both facts from the journal, never from a plan.
- `ConversationSyncOperation` gains `cloud_thread_id: CloudThreadId` (required, non-optional — missing key is natively a deserialization error) and keeps `thread_id` required and local — ops are constructed at apply, after minting.
- **Wire discipline for the optional fields** (`binding.cloud_thread_id`, action `thread_id`, action `cloud_thread_id`): **present-on-wire, nullable** — always serialized (explicit `null` for `None`, no `skip_serializing_if`) and deserialized through a presence-requiring `deserialize_with` helper. This is load-bearing, not style: a plain `Option<T>` field deserializes to `None` on a *missing* key even without `#[serde(default)]`, and `deny_unknown_fields` rejects extra keys but never makes keys required — so without the helper, a pre-cutover `CreateCloud` action (old `thread_id` string, no `cloud_thread_id` key, retired keys omitted-when-`None`) would deserialize as a *valid* new-shape action and silently execute under apply-minting, and old binding rows would silently load as unmapped. With the helper (which disables serde's implicit-`Option` tolerance, making the key mandatory), every pre-cutover bindings, plan, and journal document fails closed on the missing keys; `deny_unknown_fields` separately rejects documents still carrying retired keys with values. These documents are local-only, so the changed `None` serialization affects no content digests. No migration.
- No new stale-pin is needed for the mapping: every bindings mutation (including a keep-both clearing a mapping) bumps `bindings_document_revision`/`binding_revision`, which apply already re-validates (conversation_sync.rs:154-161).
- Plan-time **reserved-target expectations for minted-identity files disappear** (their paths are unknowable at plan time). The identity-independent pins stay — local source digest, index-file expectation, the in-place (non-codex) MaterializeCloud transcript target, revisions/tails/generations — and destination absence is asserted at apply instead (D2).

**D6 — Review joins through the mapping only.** The union-of-ThreadIds loop seed (commands.rs:5569-5575) is replaced by review units pairing a local row with the cloud row its mapping names. Unbound local sessions **never** match a cloud row — the derived-id rendezvous is deleted, not just unused, and D1's namespace split makes it unconstructible. Unclaimed cloud rows are cloud-only units keyed by their cloud id. Journal-pending blocking covers **both** ids of every operation as two *typed* sets — pending `ThreadId`s and pending `CloudThreadId`s, each checked only against its own side, so a string coincidence across spaces can never falsely block an unrelated row (and can no longer exist anyway). A pending CreateLocal blocks the cloud-only row a fresh review would re-offer (via `op.cloud_thread_id`); if its half-materialized file is already discoverable, that local row derives `initial_conversation_thread_id(…, p_b) == op.thread_id` and is blocked by the local set.

**D7 — Provenance stays in the portable (cloud) id space on both sides.** `preserved.preserved_from` and `forked_from` are `CloudThreadId`-typed on cloud rows *and* on binding rows (the type carries the space). Push (CreateCloud carries `binding.preserved`/`binding.forked_from`, commands.rs:8478-8492) and Pull (rows copy `prepared.cloud_preserved`/`cloud_forked_from`, commands.rs:11289, 11320-11321) keep copying **verbatim** — no translation layer. The apply-minted keep-both provenance names the divergent thread's cloud id, and the ordinal max-scan (today at commands.rs:6435-6448) compares cloud-space against cloud-space on both inputs. Provenance is display-only and tolerates dangling references, exactly as documented today (lib.rs:1763-1769).

**D8 — `ConversationThread.source_thread_id` stays, redefined as a content fact.** It names the provider session id embedded in the stored transcript bytes (the pusher's local session id under the Encode build). It is consumed only as content/context — builder self-verification (codex_standalone_builder.rs:213), adapter `source_provider_session_id` hints (Claude sidecar renaming), display fallbacks — never for identity or matching. With derivation gone, knowing it determines nothing. (The alternative — reidentifying published content to a neutral id — would force a third id per thread for zero benefit, since pull rewrites the embedded id anyway.)

**D9 — KeepBoth keeps today's shape, translated — with its identities minted at apply.** The existing row stays the cloud-tracking thread: it keeps its local `thread_id` and its `cloud_thread_id`, receives the fresh provider alias + imported layout + materialized bytes. The divergent local branch is re-keyed to the preserved ThreadId **with `cloud_thread_id` cleared** and provenance set — an ordinary local-only thread whose later push mints a fresh cloud id (today's "preserved branch is MissingCloud" behavior, preserved). Remote alias, preserved ThreadId, ordinal, and marker title are all minted/composed inside `apply_prepared_pull_conversation` and journaled (`KeepBothJournal`, `bindings_after`, the hash-pinned index intent payloads).
*Rejected:* the inverse (preserved branch keeps its id, new row tracks the cloud) — it changes the synced thread's local identity on every divergence and invalidates other links' checkpoints semantically rather than mechanically, for no benefit.

**D10 — Accepted losses (by design, not oversights):**
- **No identity recovery without the mapping.** If binding rows are lost (bindings document wiped, project re-registered), the machine's threads are local-only again; pulling re-materializes cloud threads as new local threads and pushing mints new cloud ids. Today's derived-id reclaim after re-registration worked only for born-local pushed threads anyway (pulled threads already duplicated); now it is uniformly gone. Mapping lifetime == binding-row lifetime.
- **Out-of-band copies never rendezvous.** A rollout file copied between machines by hand reviews as an unrelated local-only thread.
- **Conflicts surface at apply, not at review.** With reserved-target pins gone for minted identities, an occupied destination is a per-action apply failure (receipt) instead of plan staleness.

## Design — flow walkthroughs

**Push, unmapped thread (first publish).** Review derives `t_a` (no binding row yet for a never-synced thread); push planning builds `CreateCloud` with `thread_id = Some(t_a)`, `cloud_thread_id = None`. Apply (`build_publish_request`) confirms the live row (if any) is still unmapped, mints `t_c`, fails hard on any conflict (D2); it then builds the manifest row, transcript at `state/conversations/<provider>/<t_c>/transcript.jsonl`, recipe entry and resource id under `t_c`; the journaled `bindings_after` creates/updates the row with `provider_thread_id`, layout, and `cloud_thread_id = Some(t_c)` (lib.rs comment at 2159-2162: publishing commits the binding after-state); `sync_config_after` upserts the checkpoint keyed `t_a`. The journal is written only after the mint, so recovery installs the journaled documents verbatim; its content witness matches `(op.cloud_thread_id, tail_after)` against the manifest.

**Push, mapped thread.** `Publish`/`CreateCloud` carries `Some(t_c)` from the binding at review time. Apply cross-checks it against the live row: a mismatch in either direction (action `Some(x)` vs row `Some(y)`, or action `None` vs row `Some`) is a hard build error, never an adoption.

**Pull, cloud-only row (`CreateLocal`).** Review shows a cloud-only unit keyed `t_c`; the plan action carries `thread_id: None`, `cloud_thread_id: Some(t_c)`, and no provider identity. Apply mints `p_b`, assigns `t_b = initial_conversation_thread_id(bundle, provider, p_b)`, computes the adapter targets under `p_b` and fails the action if any is occupied, reconstructs/reidentifies content to `p_b` (existing Decode/rewrite path), then journals: op keyed `t_b`, `bindings_after` row `(t_b, p_b, cloud_thread_id = Some(t_c))` with cloud provenance copied verbatim, checkpoint keyed `t_b`. Recovery, receipts, and review blocking all read `t_b`/`p_b` from the journal.

**Pull, mapped thread (`MaterializeCloud` / `AdoptCloudMetadata`).** Cloud row found via the mapping; local row/checkpoint operations keyed by the local id exactly as today. Non-codex MaterializeCloud stays in-place under the row's existing provider id (no minting; `replace_existing` semantics unchanged); codex copy-on-write relocation mints its fresh provider alias at apply. The other mechanical change is `find_conversation(&action.cloud_thread_id)`.

**Pull, divergence (`KeepBoth`).** Per D9. Apply mints the remote provider alias and the preserved ThreadId, computes the ordinal over the pinned snapshot's provider scope ∪ live bindings provenance, composes the marker title (base-title inputs — local descriptor name, cloud `display_title` — travel in the prepared item), and journals everything; the minted provenance names `action.cloud_thread_id` as `preserved_from`.

**Second storage of the same bundle.** A pushes the same `t_c` to S2 (mapping reuse). B's binding `(t_b ↔ t_c)` matches S2's row on B's first review of S2; the existing adoption probe (rows **without an accepted pin** whose cloud side is present, commands.rs:5663-5672) refolds local bytes against the cloud tail and seeds S2's acceptance without a download. The probe becomes mapping-driven instead of id-equality-driven and otherwise survives verbatim — as does re-linking a removed storage (checkpoints die with the link; bindings and mappings survive).

**What the cloud never learns:** `t_a`/`t_b`, binding documents, checkpoints, or any mapping. It stores `t_c`-keyed rows whose only local residue is the descriptive `source_thread_id`/embedded session id (D8).

**Codex subagents: outside the identity system, unaffected — three interactions recorded.**
*Shipped today*, subagent rollouts are excluded from conversation sync entirely: capture never surfaces them as threads (`excluded_subagent_session_ids`, provider_capture.rs:122-124/293-302) and Pull refuses stored internal-subagent transcripts (`is_internal_subagent`, commands.rs:6083-6093). They receive no ThreadId, binding, checkpoint, or cloud row, so nothing in this plan touches them; the one shared code path — the pull-side refusal running over cloud-only rows — is already covered by the Stage 3 prefetch-filter change.
*The planned transport* (docs/PLAN_CODEX_SUBAGENT_CLOSURE_TRANSPORT.md, not yet implemented) is compatible by construction, because it deliberately keeps children outside the identity system: byte-verbatim files under their **original provider thread ids**, "no ThreadId, binding, checkpoint, layout, index row, or portable tail" (§2), `mint_provider_thread_id` never called for children (§5). Three interactions to carry into that work:
1. Children's logical namespace `state/conversations/{provider}/{thread_id}/subagents/{basename}` (§2) follows the **parent's manifest key**, which becomes the cloud id `t_c` — mechanical; whichever plan lands second amends the other's wording (Stage 9).
2. `pinned_subagent_sources` pins **existing local files** at push planning (§3) — identity-independent pins, legal under D2, which bans minting fresh identities at plan time, not pinning existing state.
3. Children keeping their original provider ids verbatim across machines is that plan's own documented decision (simplicity-first; the dangling child back-edge to the pusher's parent provider id is its accepted cost, §2) — a deliberate exception to reidentification that this plan does **not** extend the mapping to. Parent-side child references (`agent_thread_id`) are provider-id references to verbatim children and stay valid; the back-edge dangling already exists today because parent provider ids are already minted fresh per machine.

**One row-key rule, shared by the two backends the frontend joins.** Activity rows (`ProjectSessionSummary.resource_id`) and comparison rows (`ThreadSyncEntry.conversation_resource_id`) are joined by string equality in the frontend (ProjectActivityPage.tsx:359-370), so both must key rows identically: **`<provider>:conversation:<local id>` whenever a local side exists, `<provider>:conversation:<cloud id>` for storage-only rows**. Because the two namespaces are prefix-disjoint (D1), the two key forms can never collide — an unbound local row and an unclaimed cloud row always produce distinct keys, so the frontend `Map` and Activity's keyed merge cannot collapse or misclassify them even against a hostile manifest. Storage-only rows cannot navigate to session detail (gated on `source !== "remote_only"`, ProjectActivityPage.tsx:1067-1070), so session detail and the session-action/deep-link ownership guards (project_activity.rs:1310, 1375; session_detail.rs:714) only ever receive local-space resource ids and keep working unchanged. Receipts also stay local-space (`conversation_resource_id(provider, <op's local id>)`), which keeps `historical_owners` (project_activity.rs:641-679, parse-and-compare at 668) consistently local.

## Performance impact estimate

No path gains network I/O, file I/O, or cache invalidation; the deltas are in-memory work over documents every path already loads, plus one *relocation* of genuinely expensive work off the interactive path.

| Path | Delta | Magnitude |
|---|---|---|
| Status/refresh review (Observe) | id-union seed → unit join: one extra `claimed` set + mapping field reads over the already-loaded bindings doc; typed pending sets | ~µs per 100 threads; **≈ 0**. Watch-service caches keep their keys (local ids/paths) — hit rates and the milestone-8 "quiet review reads zero bytes" property unchanged |
| Pull plan build (review) | **removes** per-row `mint_provider_thread_id` — the CLI-first codex allocator spawns a `codex app-server` per allocation (codex_thread_allocator.rs:248; init handshake, 10s-bounded) — plus per-row target `stat()`s and keep-both ordinal/title work | **improvement**: ~50-300 ms saved per materializable codex row when the CLI path engages; a review offering 10 CreateLocals stops paying seconds it paid even when nothing was applied |
| Push plan build | review never minted here | 0 |
| Push apply | + one 12-byte `getrandom` per new thread; + conflict set built once per batch over the in-memory previous manifest + bindings; + journal uniqueness scans (pending ops ≈ 0-few) | <1 ms per batch at 1k manifest rows; noise next to artifact reconstruction, sha256 over transcripts, upload + CAS |
| Pull apply | gains the **moved** allocator spawn per approved codex materialization + moved target `stat()`s + one journal pre-check (fold to one journal load per batch) + keep-both composition | same total work as today, shifted from review to the apply that actually uses it; apply latency +~50-300 ms per approved codex action. Optional lever if that matters: `allocate_codex_thread_ids(count, …)` already batches — one spawn per pull batch instead of per action |
| Activity build | + one cloud→local map over scoped binding rows + O(remote) typed lookups | µs; session scans/summary cache unchanged |
| Storage / network | same object count, same round trips, no manifest shape change; `cloudthread-` + 24 hex is 3 chars shorter than derived ids | 0 |
| Local disk | explicit `"cloud_thread_id": null` on unmapped rows/actions; +1 id field per journal op | ~25 B per row; KBs total |
| Memory | +`Option<CloudThreadId>` per review unit + `claimed` set; prepare retains `LocalSessionView`s it previously dropped (metadata-only, no bytes) | ~50-100 B/thread; tens of KB at 1k threads |
| Frontend | +1 bool per entry; same map sizes | 0 |

## Risks

- **Two concentrated blast radii: the review-loop join and the pull-apply identity block.** The unit-pair join replaces the most load-bearing implicit assumption in `provider_thread_review`; moving all minting into `apply_prepared_pull_conversation` restructures its head (identity resolution + target computation) while classification/evidence/pins and the engine's staging/commit/recovery mechanics stay untouched. Everything else is field-plumbing.
- **Conflicts now surface at apply, not at review.** Accepted per user decision ("if there is a conflict, just fail it"); per-action failure receipts keep the rest of a batch applying, and the engine's no-clobber commit remains the last-line guard.
- **Missed id-equality join somewhere peripheral.** Largely retired by D1: the distinct `CloudThreadId` type makes cross-space comparison a compile error on every typed field, and prefix-disjoint namespaces make stringly joins (resource ids, row keys) collision-free. The residual risk is only code that lifts ids into untyped strings; guard: the grammar/boundary tests plus grepping every `find_conversation` / `scope.conversations.get` / `.thread_id ==` site during implementation. Known-complete: adapters/codecs/capture/CLI carry zero mallard ThreadIds; no Tauri command takes a bare ThreadId.
- **Serde silent-compat hazard.** `Option` fields tolerate missing keys and `deny_unknown_fields` cannot make keys required — the presence-requiring `deserialize_with` discipline (D5) is what actually delivers fail-closed on pre-cutover documents; dropping it during implementation would silently re-open the old-plan execution hole. The Stage 8 missing-key cutover tests pin it.
- **Retry-duplication hazard.** Apply-time minting makes retried CreateLocals mint fresh local ids, which the old local-id-only journal guard cannot correlate; the D2 journal uniqueness by `cloud_thread_id` + `(plan_id, plan_action_id)` is the closure, pinned by the failpoint retry test.
- **Frontend presence-gate regression.** `cloud_thread_id` presence currently doubles as "row came from a storage comparison"; making it honest without the `compared_against_storage` flag would silently reroute two UI branches. The flag ships in the same change.
- **Provenance space mismatch** is now a type error rather than a display risk — `CloudThreadId`-typed provenance can't hold a local id.
- Old plans/journals/bindings in a stale `~/.mallard` fail closed via the presence-required and retired fields — intended; the wipe makes it moot.
