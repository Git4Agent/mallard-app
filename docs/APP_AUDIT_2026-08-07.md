# Mallard application audit

**Audit date:** 2026-08-07  
**Application version:** 0.1.2  
**Source baseline:** `3d6b7234327a` plus the pre-existing uncommitted working tree  
**Scope:** active React/Tauri product path, project sync, Library, persistence,
storage transports, tests, documentation, and release configuration

This is a snapshot audit. The working tree contains an in-progress Rust
workspace reorganization, provider-neutral Activity/session detail work, and
the draft-linked Library. Findings should be rechecked after those changes are
committed or replaced.

## Executive assessment

Mallard has a strong integrity and restore-safety core: validated domain IDs,
bounded and no-follow filesystem access, immutable content-addressed objects,
SHA-256 binding, compare-and-swap publication, immutable review plans, guarded
apply, backups, receipts, and crash journals. The provider registry and the
separate Library bounded context are also meaningful architectural advances.

The current build is suitable for continued development and controlled tester
use, but it is not ready for unattended production use with confidential team
data. The immediate reasons are:

1. the standard backend command omits 177 domain and infrastructure tests;
2. normal changes have no CI, and the release workflow runs no Rust tests;
3. remote manifest sizes are not protocol-bounded before download and parsing,
   and provider capture reopens checked paths in a way that can follow a
   concurrent replacement;
4. two confirmed UI defects can lose draft edits or present a failed Library
   Pull as a success;
5. portable transcripts and Library payloads have no application-layer
   encryption, while R2 credentials are stored and returned to the webview as
   plaintext strings; and
6. the advertised CAS guarantee assumes, rather than proves, that a configured
   S3-compatible endpoint honors conditional writes.

The recommended order is to repair the verification gate and confirmed UI
failures first, then close the confidentiality and storage-capability gaps
before broadening access.

## Audit method and limits

The review used the current source rather than historical `PLAN_*` documents.
It covered static architecture and data-flow inspection, targeted searches for
safety and coupling patterns, current documentation, and the committed build
and test commands.

It did not use a real `~/.mallard`, provider home, S3/R2 account, or project
checkout; run a penetration test; audit third-party dependencies against live
advisory feeds; or exercise the packaged Tauri application through a real
WebView. No finding should be read as a claim that those untested surfaces are
safe.

## Current architecture

```text
React shell
  |-- project-sync UI -------- projectSyncApi -----+
  |-- Library UI ------------- storageCatalogApi --| typed Tauri invoke
  `-- neutral sync-review primitives               |
                                                    v
Tauri command boundary
  |-- project_sync::commands: project orchestration and transactions
  |-- storage_catalog: independent per-resource Library protocol
  `-- activity_log: sanitized local operational history
                    |
                    v
Rust workspace
  |-- mallard-domain: IDs, schemas, validation, plans, manifests, digests
  `-- mallard-infrastructure
       |-- provider registry and Codex/Claude adapters
       |-- discovery, capture, Activity, and session detail
       |-- persistence and crash recovery
       |-- bundle publication, restore planning, backups, and apply
       `-- storage_core: closed keys, local store, S3/R2 store, marker
                    |
          +---------+-------------------+
          v                             v
provider/project files             portable object storage
```

The project Push path is discovery and review, exact capture, immutable object
and manifest publication, then one CAS update of the mutable head. Pull is
inspect, immutable plan, explicit selection, lazy verified download, guarded
apply, backup/receipt, and local baseline update. The Library uses a separate
per-resource repository and plan/apply protocol over the same neutral storage
transport.

The workspace reorganization is not complete. The Tauri project-sync module
still exposes temporary re-export shims explicitly scheduled for removal
([`project_sync/mod.rs:8`](../src-tauri/src/project_sync/mod.rs#L8)), while the
command layer remains the main integration point.

## Strengths to preserve

- Domain values fail closed during parsing and validation. Portable manifests
  bind scopes, resources, logical paths, digests, conversation lineage, and
  review coordinates instead of trusting timestamps.
- Payload objects, manifests, and commits are immutable; the head is the only
  mutable project pointer. Publication writes content first and swings the head
  with CAS last ([`bundle_engine.rs:778`](../crates/mallard-infrastructure/src/bundle_engine.rs#L778)).
- Restore and conversation operations are plan-based, digest/revision pinned,
  expiring, journaled, and backed up. Deletion is exact and opt-in.
- Local persistence uses bounded reads, revision checks, no-symlink checks,
  private Unix permissions, synced temporary files, atomic replacement, and OS
  file locks ([`persistence.rs:580`](../crates/mallard-infrastructure/src/persistence.rs#L580)).
- The provider registry is descriptor-driven and proves a third provider can
  traverse common discovery and capture without adding a provider branch
  ([`registry.rs:27`](../crates/mallard-infrastructure/src/providers/registry.rs#L27)).
- Project sync, neutral review primitives, and the Library have separate
  frontend API/model/type boundaries. Raw Tauri calls are centralized.
- Session detail is lazy, snapshot-pinned, cursor-bounded, and request-guarded.
  Markdown does not enable raw HTML and filters unsafe link protocols.
- The full Rust workspace suite is substantial and safety-focused: 342 tests
  pass when it is actually invoked. The fast frontend suite passes 158 tests
  covering pure decision rules, static markup, accessibility contracts, and
  command-surface freezes.
- Activity logging is bounded, retained locally, structured, and sanitized
  before persistence.

### APP-001 — Standard backend scripts omit 177 core tests

The Rust workspace contains the Tauri, domain, infrastructure, and placeholder
CLI packages ([`Cargo.toml:1`](../Cargo.toml#L1)), but
`test:backend-integration` targets only `src-tauri/Cargo.toml`
([`package.json:14`](../package.json#L14)). That command ran 165 tests. The
workspace command ran 342: the same 165 plus 31 domain and 146 infrastructure
tests. In other words, the documented aggregate suite currently skips the
tests closest to manifests, persistence, provider capture, bundle apply, and
storage transport.

**Recommendation:** change the package script and every documented handoff
command to `cargo test --workspace --lib`. Keep a fast Tauri-only command only
if it is named as partial. Add a regression check that each workspace library
test binary is discovered.

### APP-002 — Normal changes have no CI and releases run no Rust tests

The only workflow triggers on `v*` tags
([`release.yml:3`](../.github/workflows/release.yml#L3)). It runs frontend and
release-configuration tests, but no Rust suite before packaging
([`release.yml:42`](../.github/workflows/release.yml#L42)). A pull request can
therefore merge with no automated check, and a tagged release can package a
backend regression.

**Recommendation:** add a push/pull-request workflow for `npm run build`, the
frontend suite, release-config tests, `cargo test --workspace --lib`,
`cargo fmt --all -- --check`, and Clippy. Make release packaging depend on the
same successful gate.

### APP-003 — Failed or partial Library Pulls render as success

Library outcomes explicitly support `partial` and `failed`, and Pull reports
whether the remote baseline was accepted
([`types.ts:341`](../src/components/storage-catalog/types.ts#L341)). The page
even creates “Pull did not advance…” copy when `remote_accepted` is false
([`StorageLibraryPage.tsx:329`](../src/components/storage-catalog/StorageLibraryPage.tsx#L329)),
but it stores every result as an untyped string and always renders that string
with a success callout and check icon
([`StorageLibraryPage.tsx:733`](../src/components/storage-catalog/StorageLibraryPage.tsx#L733),
[`StorageLibraryPage.tsx:1027`](../src/components/storage-catalog/StorageLibraryPage.tsx#L1027)).
This violates the review-first promise at exactly the point where the user
needs to know whether local state changed.

**Recommendation:** store a typed outcome (`success`, `partial`, `failed`,
`attention`) and render it through the shared outcome primitive. Add mounted
tests for partial apply, failed apply, and `remote_accepted=false`.

### APP-004 — Closing setup can lose the latest draft edits

Project setup persists edits after a 700 ms debounce, and effect cleanup
cancels the pending save
([`ProjectSetupWorkspace.tsx:156`](../src/components/project-sync/ProjectSetupWorkspace.tsx#L156)).
The close path remains available and says the draft is kept, but it neither
flushes nor awaits that pending save
([`ProjectSetupWorkspace.tsx:509`](../src/components/project-sync/ProjectSetupWorkspace.tsx#L509)).
A save error also clears the dirty marker before the request and does not
restore it, leaving finalization blocked until another edit.

**Recommendation:** implement `flushPendingDraft()` and await it before close,
navigation, or finalization; restore dirty state after failure and expose an
explicit retry. Cover close-before-debounce and save-failure recovery with a
client effect test.

### APP-005 — Portable content has no application-layer encryption

Project publication sends captured bytes directly to content-addressed objects
and serializes the manifest directly to storage
([`bundle_engine.rs:778`](../crates/mallard-infrastructure/src/bundle_engine.rs#L778),
[`bundle_engine.rs:811`](../crates/mallard-infrastructure/src/bundle_engine.rs#L811)).
Library publication similarly hashes and uploads raw skill/pet payload bytes
([`resource_engine.rs:377`](../src-tauri/src/storage_catalog/resource_engine.rs#L377)).
No encryption or AEAD dependency or envelope exists in the active path.

TLS and bucket-side protections may protect transport and infrastructure, but
any principal able to read the storage can read transcripts, summaries,
project files, skills, and pet assets in their application representation.

**Recommendation:** define an encrypted portable-envelope version before broad
team use. Compress then encrypt payloads with an authenticated cipher, encrypt
sensitive manifest content, bind routing metadata as associated data, and keep
the existing integrity/CAS chain over the stored representation. Document key
recovery, sharing, rotation, and loss behavior before implementation.

### APP-006 — S3 credentials are plaintext local and webview data

`StorageConfig` owns `access_key_id` and `secret_access_key` as serialized
strings ([`mallard-domain/src/lib.rs:714`](../crates/mallard-domain/src/lib.rs#L714)).
The complete config is written to `sync_config.json`
([`persistence.rs:588`](../crates/mallard-infrastructure/src/persistence.rs#L588))
and returned by `get_project_sync_config`
([`commands.rs:947`](../src-tauri/src/project_sync/commands.rs#L947)), so the
secret is also held in React/webview state. Unix mode restrictions and
no-follow persistence reduce exposure but do not provide secret-store or
process isolation.

**Recommendation:** store secrets in the OS credential store and persist only
an opaque credential reference. Split public storage settings from secret
write/update commands, never return an existing secret to the webview, and
migrate existing configs and setup drafts with explicit rollback behavior.

### APP-007 — Conditional-write support is not proved

The storage model has an optional `supports_conditional_writes` field, but new
UI-created storage omits it
([`StorageSettings.tsx:85`](../src/components/project-sync/StorageSettings.tsx#L85)).
The S3 store rejects only an explicit `Some(false)` and accepts `None`
([`s3_store.rs:48`](../crates/mallard-infrastructure/src/storage_core/s3_store.rs#L48)).
No production probe populates the field. Cloudflare R2 may satisfy the
requirement, but the generic S3-compatible contract is broader than that one
service.

If an endpoint ignores `If-Match` or `If-None-Match`, the advertised
single-winner head publication can degrade into last-writer-wins behavior.

**Recommendation:** probe conditional create and update when saving storage,
persist the verified capability with a probe version/time, and fail closed if
support is absent or inconclusive. Re-probe when the endpoint or bucket
identity changes.

### APP-008 — Remote manifest sizes have no protocol maximum

`BundleHead::validate` requires a nonzero `manifest_size` but applies no upper
bound ([`mallard-domain/src/lib.rs:4185`](../crates/mallard-domain/src/lib.rs#L4185)).
Current and historical reads pass that remote value directly to verified
staging before parsing
([`bundle_engine.rs:968`](../crates/mallard-infrastructure/src/bundle_engine.rs#L968)).
The S3 implementation will stream until the caller-supplied expected size
([`s3_store.rs:206`](../crates/mallard-infrastructure/src/storage_core/s3_store.rs#L206)).
The Library head/read path has the same ordering problem: the manifest is
staged from its declared size before the later in-memory bound is applied
([`resource_engine.rs:195`](../src-tauri/src/storage_catalog/resource_engine.rs#L195)).

A corrupted or modified storage can therefore force excessive bandwidth and
temporary-disk use; project JSON parsing can also allocate from an
attacker-sized document before collection validation rejects it.

**Recommendation:** define one explicit project-manifest maximum and one
Library-manifest maximum, validate them in both head and publication types,
reject an oversized declaration before staging, and retain bounded parsing as
a second line of defense. Add local and S3 tests with a valid head/digest that
references an oversized manifest.

### APP-009 — Provider capture reopens checked paths unsafely

Capture canonicalizes and no-follow inspects a source, then performs separate
metadata/size accounting, but finally loads it with path-based `fs::read`
([`provider_capture.rs:315`](../crates/mallard-infrastructure/src/provider_capture.rs#L315),
[`provider_capture.rs:346`](../crates/mallard-infrastructure/src/provider_capture.rs#L346)).
That last operation follows a replacement symlink and does not bind the bytes
to the inode or size that passed review. A concurrent provider/editor process
can also append past the per-file or aggregate budget between metadata and
read.

This is a safety-invariant violation even when exploitation is unlikely: the
reviewed file identity and budget are not necessarily the bytes later
published.

**Recommendation:** open each source once with no-follow semantics, verify the
opened descriptor and approved-root relationship, perform a bounded read from
that descriptor, and recheck identity/size before accepting the bytes. Use the
same helper for provider and optional project content capture, with failpoint
tests for append, rename, and symlink replacement.

### APP-010 — Async results can cross UI boundaries

Three current paths lack complete request identity checks:

- rapid project changes can let an older `loadProjectData` completion replace
  the selected project's shared detail, inventory, and readiness
  ([`ProjectSync.tsx:938`](../src/components/project-sync/ProjectSync.tsx#L938));
- Library category changes invalidate load/inspection work but not every
  finalize, plan, Push, or Pull continuation
  ([`StorageLibraryPage.tsx:95`](../src/components/storage-catalog/StorageLibraryPage.tsx#L95));
- changing setup drafts can briefly retain the previous draft's inspection and
  enable actions against stale candidates
  ([`StorageLibraryPage.tsx:436`](../src/components/storage-catalog/StorageLibraryPage.tsx#L436)).

**Recommendation:** give every controller an epoch containing host, project or
category, resource/draft ID, and request sequence. Check it before every state
write. Clear derived state synchronously when identity changes, and disable or
cancel navigation while a mutation cannot safely move with the user.

### APP-011 — Production CSP is disabled

Tauri explicitly sets `"csp": null`
([`tauri.conf.json:28`](../src-tauri/tauri.conf.json#L28)). React escaping and
the session-detail Markdown protocol filter are valuable primary controls, but
conversation and tool content are untrusted inputs and an XSS in a desktop
webview reaches a privileged IPC surface.

**Recommendation:** add a production CSP with the narrowest required script,
style, image, connection, and Tauri IPC sources. Add a packaged configuration
test so development allowances cannot silently ship.

### APP-012 — Current documentation materially drifts from the app

`README.md` advertises `TECHNICAL_REPORT.md` as the current schema and boundary
authority, but the report names removed module paths, lists the obsolete
`chat_history_cache.json`, omits the Library state, describes a removed final
Review step, and carries obsolete test totals
([`TECHNICAL_REPORT.md:50`](../TECHNICAL_REPORT.md#L50),
[`TECHNICAL_REPORT.md:90`](../TECHNICAL_REPORT.md#L90),
[`TECHNICAL_REPORT.md:238`](../TECHNICAL_REPORT.md#L238)). `AGENTS.md` likewise
points at the old in-crate domain path and removed `chat_history.rs`
([`AGENTS.md:43`](../AGENTS.md#L43)).

The README walkthrough uses “Project History,” “Open ChatGPT Desktop,” and a
final Review step even though the current UI uses Activity/session detail,
“Open in Codex,” and only Git & sessions plus optional Project files
([`README.md:103`](../README.md#L103),
[`reviewSteps.ts:3`](../src/components/project-sync/reviewSteps.ts#L3)).

**Recommendation:** update README, AGENTS, and TECHNICAL_REPORT together after
the reorganization lands. Add `docs/README.md` classifying current authority,
active proposals, and historical plans; use a link checker to prevent stale
source references.

### APP-013 — Frontend tests miss client and native behavior

The frontend runner bundles 11 manually enumerated test files with esbuild and
executes Node's test runner
([`run-frontend-integration-tests.mjs:10`](../scripts/run-frontend-integration-tests.mjs#L10)).
Tests use server rendering and source assertions; there is no client DOM effect
runner, real browser/WebView, dialog, IPC, or packaged-app automation. `tsc`
checks `src` but not `tests`, while esbuild transpilation does not perform
semantic TypeScript checking.

That gap directly explains why the debounce, outcome-tone, and overlapping
request defects pass all 158 tests.

**Recommendation:** add a test `tsconfig`, automatically discover test files,
and add a small mounted interaction suite for async controllers. Add a minimal
native smoke path for startup, storage creation, setup, reviewed Push/Pull,
Library plan/apply, and command serialization.

### APP-014 — Orchestration is concentrated in large modules

Measured in this snapshot:

- `ProjectSync.tsx`: 3,106 lines and 73 `useState` calls;
- `ProjectActivityPage.tsx`: 2,045 lines;
- `StorageLibraryPage.tsx`: 1,071 lines;
- `App.css`: 12,092 lines; and
- `project_sync/commands.rs`: 19,028 lines, with production code extending to
  roughly line 13,332 before its main test module.

The resulting controller contains several different request-token schemes and
shared state cells, and state setters are called from inside other functional
state updaters in some Push paths. These are maintainability risks and are
already producing identity-race defects.

**Recommendation:** split shell load, project selection, Push, Pull, activity
log, storage editing, and Library operations into explicit reducers/controllers.
Split Tauri commands by capability behind thin wrappers. Finish removing the
temporary re-export shims, and split CSS by tokens and bounded surface without
changing the product cutover.

### APP-015 — Formatting and lint gates are absent and currently fail

The repository documents rustfmt conventions, but exposes no format, Clippy,
ESLint, or aggregate check script. In this snapshot:

- `cargo fmt --all -- --check` failed with formatting diffs; and
- `cargo clippy --workspace --all-targets -- -D warnings` failed on current
  domain and infrastructure code/tests.

These failures may be normal for the in-progress working tree; the problem is
that no automated boundary detects them.

**Recommendation:** make formatting and Clippy clean, add scoped lint
configuration for intentional exceptions, then gate both in CI. Add a
TypeScript linter for correctness rules that `tsc` does not cover.

### APP-016 — Library plans and journals under-bind executable targets

Library Pull/Fork validation checks target identities and digests but does not
fully rederive or bind every stored `target_path` to its reviewed resource
target, and native plugin plans lack a validation step that reconstructs the
approved argv
([`storage_catalog/domain.rs:2304`](../src-tauri/src/storage_catalog/domain.rs#L2304),
[`storage_catalog/apply.rs:919`](../src-tauri/src/storage_catalog/apply.rs#L919)).
Startup recovery likewise trusts syntactically valid local operation paths for
some rename and cleanup work. These documents are private, permission-limited
state, so this is not a direct remote exploit; it is a fail-closed gap for
local corruption, tampering, or planner bugs.

**Recommendation:** rederive target paths and native argv from the current
pinned profile/resource adapter at apply time. Validate operation kind, phase,
target, staging/backup path, and digest relationships together before recovery
can mutate anything.

### APP-017 — Pet atlas validation checks headers, not images

Pet validation reads PNG/WebP header fields to obtain dimensions but does not
decode and validate the complete image
([`codex_pet.rs:73`](../src-tauri/src/storage_catalog/codex_pet.rs#L73)). The
tests intentionally accept header-only byte arrays. A truncated or malformed
atlas can therefore be published and installed, then fail only when Codex or
another decoder opens it.

**Recommendation:** use a bounded decoder, require complete valid PNG/WebP
input, enforce decoded dimensions and pixel/resource limits, and add truncated,
corrupt-chunk, decompression-bomb, and trailing-data tests.

### APP-018 — Contracts are typed but manually synchronized

The Tauri boundary is centralized and TypeScript is strict, both of which are
strengths. However, `src/types.ts` is 1,311 lines, the Library maintains a
second hand-authored DTO file, and most Rust commands return `Result<T,
String>`. This makes DTO drift, retry ambiguity, localization, and reliable UI
branching harder.

**Recommendation:** generate or fixture-check serialized DTOs from Rust and
introduce a stable command error envelope with `code`, `message`, retryability,
and optional remediation. Preserve the existing structured session-detail
error pattern as the starting model.

### APP-019 — Transport and diagnostic hardening is incomplete

`StorageConfig::validate` does not require HTTPS for an explicit S3 endpoint,
while the S3 client attaches access credentials to the configured endpoint
([`mallard-domain/src/lib.rs:738`](../crates/mallard-domain/src/lib.rs#L738),
[`s3_store.rs:754`](../crates/mallard-infrastructure/src/storage_core/s3_store.rs#L754)).
The current R2 UI derives HTTPS, so this mainly affects manually persisted or
future generic configurations. Native plugin failure diagnostics also use a
small substring denylist before persisting command output
([`storage_catalog/adapters.rs:135`](../src-tauri/src/storage_catalog/adapters.rs#L135),
[`storage_catalog/apply.rs:934`](../src-tauri/src/storage_catalog/apply.rs#L934)),
leaving common token prefixes and URL userinfo outside the redaction model.

**Recommendation:** require HTTPS except an explicit loopback-only development
policy. Reuse the central credential sanitizer for plugin stdout/stderr, add
provider-token and URL-userinfo patterns, and prefer structured bounded error
fields over raw command output.

### APP-020 — Release posture remains tester-grade

The workflow produces only an Apple Silicon DMG, uses ad-hoc signing, is
unnotarized, and deliberately has no updater. It uses a floating stable Rust
toolchain and mutable action major tags. These limits are candidly documented
and acceptable for a tester release, but not for unattended rollout.

**Recommendation:** before a production claim, pin toolchains and action SHAs,
enforce locked dependency resolution, add dependency scanning, hard-sign and
notarize, add signed updates, exercise supported target platforms in CI, and
publish a migration policy for the current clean-cutover schemas.

## Additional UX and repository observations

- Project binding and bundle dialogs declare modal semantics but do not provide
  initial focus, a focus trap, Escape handling, or background inerting.
- Library discard, unlink, saved-home removal, and registration removal are
  immediate actions without confirmation. They retain remote content but can
  still cause costly local configuration loss.
- The frontend test runner imports `esbuild` without declaring it directly and
  manually lists every test entry, so dependency pruning or a forgotten list
  update can silently reduce coverage.
- Historical docs and fixtures include personal-looking absolute paths. Use
  neutral fixture roots consistently, even where the value is synthetic.
- The 100 MiB per-conversation limit is surfaced per session instead of
  blocking a whole project, which is good degradation. Larger-session support
  will require streaming/chunking and should be prioritized from measured user
  data rather than silently increasing the in-memory bound.
- The current release has no schema migration path. That is an explicit
  cutover policy, but it must become a versioned upgrade and recovery strategy
  before persistent user state is expected to survive normal updates.

## Remediation gates

### Gate 1 — make the current branch reliably reviewable

1. Run all workspace tests from the standard script.
2. Add PR/push CI and make release packaging depend on it.
