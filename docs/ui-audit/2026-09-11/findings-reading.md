### RD-1 · Flipping Credential redaction or "Push … children" queues every synced session for re-upload, yet Activity still says "Up to date" and the Push count leaves them out
- **Severity:** High
- **Where:** Settings → Privacy "Credential redaction", Sync "Push Codex children" / "Push Claude children"; then any project's Activity page and its Push button
- **Evidence:** The rows promise nothing about re-upload: `src/components/project-sync/SettingsPage.tsx:638-639` — "On replaces detected credentials in exported sessions and provider state. Off can export API keys, tokens, and passwords. Applies to this machine."; `:666` — "Include child conversations in Push. Pull restores the files stored in the cloud." A flip changes every synced row's export stamp (`src-tauri/src/project_sync/service.rs:6038-6047` — "row.wire_children != outgoing_stamp || row.wire_redaction.as_ref() != Some(…with_enabled(credential_redaction_enabled).stamp())"). A current row is left alone only "if !capabilities.export_settings_changed" and otherwise becomes `Action::Publish` (`crates/mallard-domain/src/conversation_reconciliation.rs:170-181`), with detail "Export settings changed" (`service.rs:6231`). The row is still reported as synced (`service.rs:3265-3267` — "TailClassification::Sync(_) | TailClassification::MissingBoth => ThreadSyncState::Synced"), so on Activity it keeps status "synced", and that string becomes the check mark's tooltip (`src/components/project-sync/ProjectActivityPage.tsx:493-494` — "case \"synced\": return { status: \"synced\", … label: entry.status_detail ?? `Up to date here and in ${storageName}.` }"). The header tally counts only `local-outstanding` (`ProjectActivityPage.tsx:565`), so the Push badge (`ProjectLinksWorkspace.tsx:2316-2318`, `:2471`) leaves these rows out entirely, and is blank when they are the only outstanding work. The Push review still includes every one of these rows: `src/components/sync-review/pullReviewStatus.ts:26` — "(isPushReviewStatus(status) || status === \"synced\") && isPushReviewDecision(decision)". Publish is a planned action, so the rows are selectable: `crates/mallard-domain/src/conversation_reconciliation.rs:113` — "Self::Publish => Some(ConversationPlanActionType::Publish)", `:244` — "selectable: action.planned_action().is_some()".
- **Impact:** A user who turns redaction back on after a period with it off sees every session marked synced and a Push count that leaves them out. Storage keeps the copies pushed under the old setting, which may include unredacted keys, until they happen to open Push. There they find the whole history queued as "synced" rows with the unexplained chip "Export settings changed", and the Push re-uploads everything. The Settings row gave no hint of either consequence.
- **Fix:** On the three rows, say what a change costs: "Changing this re-uploads every synced session on your next Push." Give these entries a non-synced status that the badge counts: the up-arrow with "Pushed with your previous privacy/agent settings — push to update". Rename the chip to "Pushed with previous settings".
- **Confidence:** confirmed from source for the glyph, count and review paths. The size of the re-upload needs a runtime check.

### RD-2 · A session Mallard can't read disappears from Activity without a word; the reason is only in the Logs drawer
- **Severity:** Medium
- **Where:** Project → Activity (the session list and the commit rail)
- **Evidence:** The backend sends the reasons with the page: `src/types.ts:1644` — "warnings: string[];" on `ProjectActivity`, filled by `crates/mallard-infrastructure/src/project_activity.rs:410-414` — "Skipped '{}': {}", `:420-423` — "Cannot read '{}': {error}", `:457` — "Skipped '{}': {error}" and `:463-466` — "Skipped '{}': the summarized session identity changed". Each is followed by `continue`, so that session gets no row. `:1275-1277` adds "Git history was limited to the newest {MAX_GIT_COMMITS} first-parent commits". Nothing on screen reads the field: "warnings" appears nowhere in `src/components/project-sync/ProjectActivityPage.tsx`, `ProjectLinksWorkspace.tsx` or `ProjectSync.tsx`. The only trace is a Logs line: `src-tauri/src/project_sync/commands.rs:564-566` — "for warning in &activity.warnings { log.emit(&app, "warning", "history.scan_warning", warning); }". The Files face, by contrast, shows its own scan warnings on the page: `ProjectFilesActivityPage.tsx:422` — "{inventory.warnings.length} scan warning{…}".
- **Impact:** A user looking for yesterday's session finds no row, no count and no notice, and concludes Mallard never captured it or lost it. The explanation, a raw file path and parser error, sits in a Logs drawer that is usually closed. A long repository likewise shows only its newest commits with no hint that older ones exist.
- **Fix:** When `activity.warnings` is non-empty, add a standing item to the Activity notice zone, for example "2 sessions couldn't be read and aren't listed. Show details", which opens Logs filtered to History or lists the files. At the foot of a truncated rail, say "Showing the newest N commits".
- **Confidence:** confirmed from source. How often a transcript fails to summarise is a runtime question.

### RD-3 · Logs stamp every line with a clock time only, across days of retained history (30 by default)
- **Severity:** Medium
- **Where:** Logs drawer (any screen → Logs), especially after "Load older logs"
- **Evidence:** `src/components/LogPanel.tsx:160-163` — "return new Intl.DateTimeFormat(undefined, clockOptions(true));" and `src/clock.ts:14-17` gives only `{ hour, minute }` plus `second`, no date fields. Each row prints it verbatim: `LogPanel.tsx:114` — `<span className="log-ts">{formatter.format(line.ts)}</span>`. The drawer loads retained entries from disk in pages (`src/components/project-sync/ActivityLogDrawer.tsx:127-133` — "queryActivityLogs({ … cursor, limit: 500 })"; `LogPanel.tsx:344` — "Load older logs"; `:356` — "Loading retained logs…"), and retention defaults to 30 days with options to 365 (`src/components/project-sync/SettingsPage.tsx:51` — "const RETENTION_OPTIONS = [7, 30, 90, 180, 365];"). The list renders rows with no day divider (`LogPanel.tsx:360-362`).
- **Impact:** A user checking when a Push last failed sees "17:05:32 push …" with no way to tell whether it was today or last week. Lines from different days run together in one column, which defeats the drawer's main use: reconstructing what happened.
- **Fix:** Group rows under day dividers, as the session timeline already does with `groupSessionEventsByDay`. Alternatively, print the short date ("Sep 9 17:05:32") on any row not from today.
- **Confidence:** confirmed from source

### RD-4 · Reset Mallard never says it removes your storages, their saved keys, and your project list
- **Severity:** Medium
- **Where:** Settings → Local data → "Reset Mallard" (row copy and the confirm dialog)
- **Evidence:** `src/components/project-sync/SettingsPage.tsx:998-1001` — "Permanently deletes everything in <code>~/.mallard</code> — sync metadata, activity logs, and the backups of files Pull replaced — clears Mallard's saved preferences, then restarts as a fresh install. Cloud revisions and your project files are not touched." · `:432` (confirm) — "Everything in ~/.mallard is deleted${sizeLine} — sync metadata, activity logs, and the only local backups of files Pull has replaced — and Mallard's settings return to their defaults. This cannot be undone.\n\nCloud revisions and your project files are not touched." What that folder actually holds: `crates/mallard-infrastructure/src/persistence.rs:420-421` — `self.root.join("sync_config.json")`, whose type is `crates/mallard-domain/src/lib.rs:1239-1245` — "pub struct SyncConfig { … pub storages: Vec<StorageConfig>, … pub projects: Vec<LocalProjectRegistration>"; `README.md:199-200` — "Credentials and machine-specific paths are stored only in Mallard's local metadata under `~/.mallard/`"; the Catalog's rows and storage links live there too (`src-tauri/src/storage_catalog/persistence.rs:149-157` — "catalog_resource_profiles.json", "catalog_scope_links.json", "catalog_scopes.json"). The wipe is `remove_dir_all` on the whole root (`persistence.rs:515`).
- **Impact:** A user reading "sync metadata" can't tell that every storage connection (R2 access keys, Dropbox sign-in), every linked project and every Catalog row goes too. After the reset they have to set up each storage again, which means finding or regenerating an R2 secret that Cloudflare only shows once, and re-add every project. "Cloud revisions … are not touched" even suggests the storage stays connected.
- **Fix:** List the losses in plain words, in both the row and the dialog: "Removes your storages and their saved keys or sign-ins, your project list and links, Catalog rows, activity logs and the only backups of files Pull replaced. What's already in your storages and your project files stays; you'll add storages and projects again after the restart." Drop "sync metadata" and "revisions".
- **Confidence:** confirmed from source

### RD-6 · A Catalog item marked "Gone from <storage>. Push to put it back." cannot be pushed
- **Severity:** Medium
- **Where:** Catalog → a Skills / Plugins / Pets page, on an item whose stored copy disappeared from the storage after it had synced (for example the storage was cleared from another machine)
- **Evidence:** The badge and badge count promise Push: `src/components/storage-catalog/model.ts:185-186` — "case \"remote_missing\": return \"local-outstanding\";", `:210-211` — "`Gone from ${storage}. Push to put it back.`", and `src/components/storage-catalog/StorageCatalogPage.tsx:938` — "if (status === \"local-outstanding\") totals.push += 1;" (the count renders inside the Push button, `:1461-1463`). But `model.ts:227-229` — "return row.local_present && (row.state === \"new\" || row.state === \"local_changed\");" leaves it out of `pushRows`. With nothing else to push, the button is disabled (`StorageCatalogPage.tsx:1451-1453` — "syncDisabled || pushRows.length === 0") and has no tooltip, because `syncDisabledReason` is undefined once a storage is chosen (`:1358-1362`). The backend refuses as well: `src-tauri/src/storage_catalog/resource_planning.rs:258-262` makes rows selectable only for "CatalogLinkState::New | CatalogLinkState::LocalChanged"; `:273-274` — "The accepted stored copy is missing from the storage"; `:297` — "held_for_pull: blocked_reason.is_some()". So when the review opens for other items, this one is counted under "N skills held for Pull" with "`${storageName} has versions this Mac has not reviewed, so their local changes cannot push yet.`" (`StorageCatalogPage.tsx:1550-1557`). Pull doesn't restore it either: `resource_planning.rs:469-473` maps it to "KeptLocal", and `model.ts:231-232` requires `remote_present` to pull.
- **Impact:** The item tells the user to Push. Push shows "1" but is greyed out with no reason, or its review says the storage holds newer versions and points to a Pull review where the item never appears. The user can't find any way to share that skill again.
- **Fix:** Let Push re-publish the local copy of a `remote_missing` item, which is what the badge promises. If it has to stay blocked, give it its own badge sentence that names the actual recovery, and keep it out of both the Push count and the "held for Pull" banner.
- **Confidence:** confirmed from source. Reaching the state requires a stored copy removed after a sync, which was not exercised.

### RD-7 · The "N agents" chip does nothing and agent rows start hidden, so reaching a subagent begins at a filter that is off
- **Severity:** Low
- **Where:** Activity → a session that used subagents → session page; then the subagent's own page
- **Evidence:** The chip is a plain span: `src/components/project-sync/session-detail/SessionDetailHeader.tsx:21-23` (FactChip → `<span className="session-detail-chip">`), used at `:93-99` with the title "`${formatSessionCount(agents)} agents spawned in this session`". The rows it counts are filtered out by default: `session-detail/sessionDetailModel.ts:94-108` — "Steps, tool calls, and agents require selection." → `agents: false`. The only way in is the "Agents" toggle in the "Show" row (`SessionDetailToolbar.tsx:38-59`), then expanding a row to reach "Open transcript" (`SessionDetailEvent.tsx:387-396`). - **Confidence:** confirmed from source

### RD-8 · Catalog Pull copy speaks protocol: "did not advance the comparison base", "local target is pinned", and a "Skip" that isn't on screen
- **Severity:** Low
- **Where:** Catalog → Pull review (an item also claimed by another storage), and the notice shown after a Catalog Pull
- **Evidence:** `src/components/storage-catalog/StorageCatalogPage.tsx:1153` — "`Pulled ${applied} ${noun(applied)}. Pull did not advance the comparison base.`" (in the "attention" tone, `:1154`); `:1721-1722` — "A different version of this local target is pinned there. Preserve a copy, acknowledge overwrite, or Skip." The review has no Skip control. A row's choices are the backend actions (`:1758-1761` via `storage-catalog/model.ts:265-275`: "Keep local as … and overwrite", "Overwrite local content", "Install stored content", "Update from storage"), and leaving an item out means unticking its checkbox, which is labelled "Exclude …" (`StorageCatalogPage.tsx:554-560`).
- **Impact:** After a Pull that only partly took, the user gets an attention notice with no next step: it doesn't say whether the items will still show as changed, or whether to pull again. The claim warning names a "Skip" they can't find, and "local target is pinned" is internal wording.
- **Fix:** Say what the partial result means for the listed items and what to do next, in plain words. Rewrite the claim note as "<storage> keeps a different version of this <skill>. Keep a copy, approve the overwrite, or untick it to leave yours as it is."
- **Confidence:** confirmed from source. The backend condition that produces `remote_accepted: false` was not exercised.

### RD-9 · The same kind of moment is printed three ways, sometimes in one column
- **Severity:** Low
- **Where:** Activity (commit headers, session rows and stored-only review rows), the session page header, Catalog rows and their tooltips
- **Evidence:** Session rows use `src/components/project-sync/ProjectActivityPage.tsx:669` → `src/clock.ts:55` — "`${fullDateFormatter.format(when)} at ${fullClockFormatter.format(when)}`" ("Sep 11, 2026 at 17:05"). The commit header directly above, whose stamp the code says "forms one column with the session stamps below" (`ProjectActivityPage.tsx:1998-2000`), prints through `formatDate` → `formatDateTime` (`:2012`; `clock.ts:31-36` — "toLocaleString(undefined, { month: \"short\", day: \"numeric\", year: \"numeric\", ...clockOptions() })", which gives "Sep 11, 2026, 17:05"). Stored-only review rows do the same (`:1489`). The session page start chip uses `session-detail/sessionDetailModel.ts:351` — "`${formatSessionDetailDay(value)} · ${formatSessionDetailClock(value)}`" ("Sep 11, 2026 · 17:05"). Catalog rows print the "at" form (`src/components/storage-catalog/StorageCatalogPage.tsx:722`) while their own tooltip reads "Edited Sep 11, 2026 · 17:05" (`storage-catalog/model.ts:256-259`). Unknown values and units drift the same way: the Activity token chip shows "Not reported" (`ProjectActivityPage.tsx:300`, rendered at `:705`) where the session page says "Tokens unavailable" (`session-detail/SessionDetailHeader.tsx:90`), and Settings offers "100 MB" (`SettingsPage.tsx:746`) while the over-limit row reason says "Session file exceeds the 100 MiB per-file sync limit." (`src-tauri/src/project_sync/service.rs:3240-3243`).
- **Impact:** Minor, but the stamp column on Activity switches shape between commit and session lines, and a Catalog row's stamp and its tooltip give two notations for the same instant. The timeline reads as if it came from different tools.
- **Fix:** Send every date-plus-time through one helper with one separator (for example "Sep 11, 2026 · 17:05"). Use one word for unknown values ("Unavailable"), and one unit spelling for sizes (MB in the backend message, or MiB everywhere).
- **Confidence:** confirmed from source. The separators shown are en-US and vary by locale.
