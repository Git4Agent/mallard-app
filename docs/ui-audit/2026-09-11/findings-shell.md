Snapshot: isolated source snapshot (0c6813e + uncommitted, 2026-09-11 17:15 PDT). Paths below are relative to it.

### SH-1 · ⌘Q during a Push or Pull quits without the "Sync in progress" warning
- **Severity:** High
- **Where:** Any screen while a Push/Pull is writing — the user presses ⌘Q or picks Mallard › Quit from the menu bar
- **Evidence:** `src/components/project-sync/ProjectSync.tsx:1044` — "getCurrentWindow().onCloseRequested(async (event) => {" is the only guard, and it carries "A sync is still writing. Quitting now can leave this project's synced state half-written, and it cannot be undone." (`:1048`). `src-tauri/src/lib.rs:183` — ".run(tauri::generate_context!())" has no RunEvent/ExitRequested handler and the app installs no menu of its own (no `ExitRequested`, `prevent_exit`, `PredefinedMenuItem` or `on_menu_event` anywhere under `src-tauri/src` or `crates`), so macOS gets Tauri's default menu, whose Quit item sends `terminate:` and never raises `onCloseRequested`.
- **Impact:** The app says that quitting mid-sync can leave half-written state that cannot be undone, but ⌘Q, the usual way to quit a Mac app, skips that warning. Only the red close button and ⌘W show it.
- **Fix:** Handle `RunEvent::ExitRequested` in Rust: while a sync is in flight, call `api.prevent_exit()` and emit an event so the webview shows the same "Quit anyway / Keep syncing" confirm. Or install an app menu whose Quit goes through the same guard.
- **Confidence:** needs runtime check (press ⌘Q during a Push). The source confirms that no Quit handler exists. The platform behaviour, where Quit maps to `terminate:` and bypasses `onCloseRequested`, comes from the 2026-08-25 frontend re-audit, which recorded this gap. It is still unfixed at this snapshot, and the 2026-08-30 and 2026-09-01 audits whose findings are excluded from this pass do not cover it.

### SH-2 · "Add storage" from a project creates the storage but never links it, and drops the user on the storage page
- **Severity:** Medium
- **Where:** First-run path: project page › "No storage linked yet" card › Add storage › Choose a storage type › setup › Finish
- **Evidence:** `src/components/project-sync/ProjectLinksWorkspace.tsx:2740-2744` — "if (availableStorages.length === 0) { setLinkingProjectId(null); onAddStorage(); return; }" means the project context is dropped. After commit, `ProjectLinksWorkspace.tsx:1380-1382` — "resetStorageSession(); setStorageDetailsExpanded(false); onOpenStorage(result.storage_id, false);" lands on the storage's own page, and the receipt is only "Connected ${storageName}." (`ProjectSync.tsx:2867`). The storage page has no link-to-project action. Its only project reference is the remove-disabled reason "Linked to N project(s) — unlink first" (`ProjectLinksWorkspace.tsx:1610`), and the sidebar rail now shows Storages, not the project.
- **Impact:** The user started from their project's "No storage linked yet" card and is told "Connected <storage>.", which reads as if the project is now connected. It isn't: they are on a different page, and the project still says "No storage linked yet". Reaching Push takes another four steps: Projects tab › project card › Link storage › pick the storage. The storage-first order works well, because setup preselects the only storage (`src-tauri/src/project_sync/service.rs:14668-14674`), but the default Projects landing steers newcomers into the project-first order, which is the one that breaks.
- **Fix:** Carry the originating project through Add storage. After Finish, link the new storage to that project, or return to the project with the link picker open and the new storage preselected, and say so ("Connected <storage> and linked it to <project>").
- **Confidence:** confirmed from source

### SH-3 · The first-run window never says what Mallard does or that a storage is step two
- **Severity:** Medium
- **Where:** Fresh install with zero projects: the default Projects landing, then the setup page
- **Evidence:** `src/components/project-sync/ProjectPicker.tsx:37` — "Pick a folder…" and `ProjectPicker.tsx:46` — "Sessions & memory travel with it". `LandingPicker.tsx:47-48` says this caption is "the only copy the empty page adds". On the setup page the only storage choice with zero storages is "None yet" (`ProjectSetupWorkspace.tsx:849`), its meaning sits only in a tooltip, "No storage linked yet — sessions stay on this computer" (`:845`), and setup offers no way to add a storage. The completion receipt is "… is set up — link storage when ready." (`ProjectSync.tsx:1643`). After "Pick a folder…", the folder dialog opens with no prompt: `ProjectSync.tsx:1459` — "open({ directory: true, multiple: false })" passes no `title`.
- **Impact:** A newcomer sees "Projects · 0 on this machine · Pick a folder…" and a five-word caption. Nothing says that Mallard carries Codex/Claude sessions between machines through a storage, which folder to pick, or that nothing leaves this Mac until a storage is added and pushed. "Travel with it" doesn't say where to.
- **Fix:** Replace the caption with one purpose sentence and the three steps: "Mallard carries your Codex and Claude sessions and memory between machines. 1 Pick the folder you run your agent in · 2 Add a storage (folder, R2 or Dropbox) · 3 Push." Mark each step done or next on the landing. In setup, put an "Add storage…" pill beside "None yet". Give the folder dialog a `title`, for example "Choose the project folder you run Codex or Claude in".
- **Confidence:** confirmed from source

### SH-4 · Second-Mac repo chooser: nothing is preselected, even the Git match, the one live action splits the histories, and rows are named by hex IDs
- **Severity:** Medium
- **Where:** Project page › Link storage › a storage that already holds this project from another Mac (the usual second-machine case after "Finish locally") › "Choose a repo from this storage"
- **Evidence:** `src/components/project-sync/BundleConnectionDialog.tsx:34-36` — "const [selectedId, setSelectedId] = useState(\"\");" is reset on every open, so nothing is selected even when a row wears "Recommended" (`:140`). The primary "Connect and review Pull" stays disabled until the user picks (`:177`). The ghost "Create separate repo" (`:170`) is live from the start, and for a link it saves the link on the project's own repo (`ProjectSync.tsx:2492-2493`). Rows are identified by "{match.bundle_id}" (`:141`) and "rev {match.revision ?? \"—\"}" (`:144`), and the header reads "Current local repo {currentBundleId.slice(0, 12)}…" (`:120`). Setup, by contrast, auto-selects a single exact Git match (`ProjectSetupWorkspace.tsx:378-402`).
- **Impact:** On a second Mac the only action you can click right away keeps this machine's sessions in a history separate from the first Mac's, and nothing on it says the other machine's sessions won't show up. The right choice depends on recognising a hex ID and a revision number. (The repo/repository wording is already owned by 2026-08-30 M07; this finding is about the default, the consequence, and the identifiers.)
- **Fix:** Preselect the single Recommended match, as setup does. Describe rows by what a person recognises, such as "Last pushed <time> · N sessions", not by ID and rev. Relabel the ghost action "Keep separate — don't share sessions with <name>" and place it after the primary.
- **Confidence:** confirmed from source

### SH-5 · Reset, Remove and Unlink confirms describe Mallard's internals instead of what the user will lose
- **Severity:** Medium
- **Where:** Project path bar › project menu › "Reset local sync state…". The same dialog is the offered way out of an irrecoverable Push/Pull error. Also sidebar › project row › trash (Remove project), and Pull review › Unlink when the remote history is missing.
- **Evidence:** `src/components/project-sync/ProjectSync.tsx:2555` — "Mallard will remove all local session bindings for this project, including restored-session path mappings. It will also forget reviewed sync bases and Pull results. Project files, provider sessions, project setup, recipes, storage configuration, and cloud data will not be deleted." The receipt at `:2583` reads "Local sync state reset — ${removed} derived record${…} removed; files and cloud data kept.", and the menu tooltip at `ProjectLinksWorkspace.tsx:2175` reads "Forget local sync bases, conversation mappings, and results; files and cloud data are kept". The error-recovery button is at `ProjectLinksWorkspace.tsx:2903-2915`. Remove project: `ProjectSync.tsx:2519` — "Only this app's project registration, links, and active binding are removed." Unlink: `ProjectSync.tsx:2706` — "Mallard will clear this project’s reviewed sync base."
- **Impact:** The user is asked to approve a repair they can't judge. "Session bindings", "restored-session path mappings", "sync bases", "recipes" and "derived records" name internals, not effects, so they can't tell whether the next Push re-sends everything or whether sessions they pulled earlier still open in the right folder. Reset is the suggested fix for a failed sync, so this dialog reaches users at a bad moment.
- **Fix:** Say, in user terms, what Mallard forgets on this Mac, what the next Push and Pull will do (compare everything again), what happens to sessions pulled earlier, and what stays untouched (project folder, agent history, storage contents). Receipt: "Reset <project> — the next Push and Pull will compare everything again."
- **Confidence:** confirmed from source. The downstream effects of a reset were not traced, so the rewritten copy needs checking against them.

### SH-6 · The Clear storage data confirm calls Catalog items "Library resources", a term the app uses nowhere else
- **Severity:** Medium
- **Where:** Storage page › "Storage and app actions" (⋯) › Clear storage data… (`ProjectLinksWorkspace.tsx:1598`, overflow label at `:1747`)
- **Evidence:** `src/components/project-sync/ProjectSync.tsx:2908` — "This deletes every synced project repository and Library resource in this storage." "Library" appears in no other user-visible string: a grep over `src`, mockups excluded, finds it only in comments and type names. The same content is called Catalog everywhere else: the sidebar tab "Catalog" (`ProjectSidebar.tsx:530`) and the landing "Catalog" / "Add resource…" (`src/components/storage-catalog/CatalogIndexPage.tsx:52-54`). The receipt counts a unit the user never sees: "${storageName} cleared — ${deleted} Mallard object${…} deleted" (`ProjectSync.tsx:2932`).
- **Impact:** This delete can't be undone and affects every machine, yet it never says in the app's own words that the Skills, Plugins and Pets the user shares through the Catalog are deleted from this storage too.
- **Fix:** "This permanently deletes every project's synced sessions and every Catalog item (skills, plugins, pets) that Mallard stored in <name>, for every machine that uses it." Receipt: "Cleared <name> — N project histories and M Catalog items deleted."
- **Confidence:** confirmed from source

### SH-7 · "Host identity unavailable" is a dead-end screen in internal language
- **Severity:** Medium
- **Where:** Startup, when Mallard cannot read or create its host identity under `~/.mallard` (for example a permission or lock-file error). The whole window is replaced.
- **Evidence:** `src/components/project-sync/ProjectSync.tsx:3236` — "Host identity unavailable"; `:3237` — "Mallard could not verify this installation, so sync remains paused."; `:3244` shows the raw backend string in the notice; `:3245-3247` Retry is the only control. `:3225-3251` returns this screen in place of the shell, so there is no sidebar, Settings or Logs. Typical backend strings here are like "open project-sync persistence lock: …" (`crates/mallard-infrastructure/src/persistence.rs:2744`).
- **Impact:** "Host identity" is a Mallard internal. "Sync remains paused" understates the problem, because the whole app is unusable. The user isn't told which folder is involved or what to check, and Retry usually repeats the same failure.
- **Fix:** Title it "Mallard can't open its data folder". Name the folder (`~/.mallard`) and the likely cause in plain words. Next to Retry, add "Show in Finder" and "Copy details" (or open the Logs drawer).
- **Confidence:** confirmed from source. The state needs a filesystem failure to reach and was not exercised. This is separate from the fixed startup-failure item: the raw JavaScript string is gone (`src/ipc.ts:13-14`) and the live-region choice is settled (`ProjectSync.tsx:3238-3244`). What remains is the internal title, the understatement, and Retry as the only exit.

### SH-9 · One failed startup read shows "Project-sync backend unavailable." and lists internal subsystem names
- **Severity:** Low
- **Where:** Shell notice zone under the bar, after launch or after ⋯ › Reload app data, when any one of the shell's reads fails
- **Evidence:** `src/components/project-sync/ProjectSync.tsx:3263` — title "Project-sync backend unavailable.". The message is `failures.join(" · ")` (`:991`), built from labels such as "Recovery: …" (`:926`), "Repository types: …" (`:957`), "Agent providers: …" (`:967`) and "Bindings: …" (`:987`). If the configuration read fails on the first load, before any config has been read, the shell renders an empty config (`:914-916`), showing zero storages and links. A later Reload keeps the last good config (`:911-912`).
- **Impact:** One failed side read, such as Git detection, puts a red "backend unavailable" over an app that otherwise works, in internal names. If the config read fails at launch, the user sees no storages at all under the same vague banner, with nothing saying their data is safe.
- **Fix:** Title the notice by effect ("Couldn't load your storages", "Some project details couldn't be loaded"), use plain names for each failed area, and say that nothing on disk or in storage was changed. Keep Retry.
- **Confidence:** confirmed from source (rare state, not exercised)

## Done well
- The fresh-install dead end reported by the 08-30 and 09-01 audits is gone. "Select a completed project to view its Codex history." has been replaced by the Projects landing, with a primary "Add project…" and a "Pick a folder…" door that opens the folder dialog directly (`src/components/project-sync/ProjectPicker.tsx:32-46`, `ProjectLinksWorkspace.tsx:1984-1996`).
- Destructive confirms consistently say what is *not* touched: "The checkout and provider files stay on disk", "No provider or storage content is touched", "Files already written to the storage location will not be deleted". Clear storage data must be confirmed with "Sync stopped — clear", not a bare OK (`ProjectSync.tsx:2519, 1544, 2953, 2909`).
- Setup never silently picks a repository. It auto-selects a single exact Git match. Otherwise it states the claim Finish will make ("Creates “X” in <storage> — machines joining this repository later will find it there"), and the button reads "Finish locally" when no storage is chosen (`ProjectSetupWorkspace.tsx:378-402, 926-928, 1017`). Default Codex and Claude homes are registered and preselected, so most users never type a profile path (`src-tauri/src/project_sync/service.rs:2009-2037, 14644-14667`).
- Startup names each stage in plain words, including the slow one, "Finishing interrupted work…" (`StartupLoadingScreen.tsx:16-23`).
- The five icon-only sidebar tabs can be learned by clicking. Each has a tooltip and an accessible name, and one click puts its name on screen: the rail heading for Projects, Catalog and Storages, the Settings page title, the Logs drawer. A disabled storage-remove button explains why in its tooltip (`ProjectSidebar.tsx:515-575, 580, 449-452`). What newcomers struggle with is the Catalog *concept* (SH-8), not the tab itself.

## Not verified

- SH-7 and SH-9 need a filesystem or IPC failure to reach, so their copy was judged from source only.
- What "Reset local sync state" does downstream was not traced: how much the next Push re-sends, and what happens to restored-session path mappings. SH-5's suggested copy needs checking against it.
- It is unclear whether the old "Project links — Choose where each project repo syncs." heading and the `profile-links-empty` block (`ProjectLinksWorkspace.tsx:2514-2535, 2608-2615`) can still appear. They render only while `editingStorage` is set with neither a saved storage nor a draft session (`:1323`, `:1984`), so at most as a brief flash. Not reported; its count string also carries the excluded "{n} storage" pluralization.
- Path-bar label truncation at the 760/640px container breakpoints (`App.css:3286-3336`) was read, not rendered. Below 760px the root crumbs above the current page drop to icons by design, and the Storages index root, being the current page, keeps its name.

- The empty sidebar rail's doors are wordless icon tiles (`ProjectSidebar.tsx:42-67`). The main landing shows the same doors with labels, so this was not reported.
