### SY-1 · Pull review opens with nothing ticked, yet Pull applies the empty selection and reports "Pull complete"
- **Severity:** High
- **Where:** Pull review — project page → path-bar **Pull**, or storage card → **Open Pull review** (first Pull on a second machine, or after "Storage has newer changes")
- **Evidence:** `src/components/project-sync/RestorePlanView.tsx:240` — `const [selected, setSelected] = useState<Set<string>>(() => new Set());` (no default; `recommendedPullSelection` only feeds the check-circle button at :302). The only gate is `:267-269` — `"Loading storage changes…"`; the footer at `:584` reads `{busy ? "Pulling…" : "Pull"}` with no count. `src/components/project-sync/pullReviewFlow.ts:78-80` — "The apply is always sent, even for an empty selection: the backend writes receipts and advances the reviewed recipe base". `src/components/project-sync/syncOutcome.ts:326-330` — title `"Pull complete"` (success tone) with stat `"0 restored"` (:295). `src/components/project-sync/ProjectSync.tsx:3184-3189` — the path-bar Pull on an open review runs the same apply ("An empty selection still applies"). By contrast, `src/components/storage-catalog/StorageCatalogPage.tsx:1384-1388, 1823` disables the Catalog's Pull at 0 ("Select at least one … to pull") and labels it `Pull {pullReviewSelectedCount}`.
- **Impact:** On a first Pull, the user sees their sessions listed and clicks Pull, or clicks the path-bar Pull a second time, which the code treats as "the second applies it". Nothing is restored, but the banner says "Pull complete" and the storage is marked reviewed, which unblocks Push. The user walks away believing the work arrived.
- **Fix:** Open the review with `recommendedPullSelection` ticked, as Push does. Put the count on the verb ("Pull 3"), matching the Catalog. With an empty selection, relabel the primary "Mark as reviewed" and title the outcome "Nothing pulled — storage marked as reviewed".
- **Confidence:** confirmed from source

### SY-2 · A project file deleted locally can never be removed from storage, though its row says "remove it during Push"
- **Severity:** High
- **Where:** Non-Git project → Activity **Files** face (row of a file deleted on this Mac) → Push review → **Project files** step
- **Evidence:** `src/components/project-sync/ProjectFilesActivityPage.tsx:74` — "Not in this folder. It remains in ${storageName}. Pull to download it here, or remove it during Push." (same sentence at `src/components/project-sync/ProjectFilesReviewPage.tsx:136`). `src/components/project-sync/PushResourceWorkspace.tsx:88-90` — Push lists only `entry.local_present && (entry.state === "local_only" || entry.state === "local_ahead")`, so a `missing` file never appears in the Push review. `src/components/project-sync/ProjectFilesReviewPage.tsx:384` renders the "Remove from storage" button only when `onToggleRemoval` is passed; `src/components/project-sync/PushResourceWorkspace.tsx:948-980` never passes it, and `src/components/project-sync/ProjectSync.tsx:1718, 1999, 2024, 3112, 3159, 3166` only ever call `setPushProjectContentRemovals(new Set())`. On the Pull side, `src/components/project-sync/pullReviewModel.ts:178-182` drops every `delete_project_file` / `delete_project_directory` action that the planner emits (`crates/mallard-infrastructure/src/bundle_engine.rs:1599, 1641`). The state is real: `src-tauri/src/project_sync/service.rs:2704` classifies a pushed file that was then deleted locally as `(None, Some(storage), Some(base)) if storage == base => "missing"`.
- **Impact:** The deletion case for non-Git projects cannot be completed. The instruction points at a control that never renders, so the file stays in storage and every other machine keeps receiving it. The Push-side deletion counts and acknowledgement in `ProjectFileCommitImpact` are unreachable.
- **Fix:** List `missing` rows on the Push files step with "Remove from storage" wired to `setPushProjectContentRemovals`. - **Confidence:** confirmed from source (control never wired; delete actions dropped). Needs runtime check: whether the next Pull re-offers the deleted file as a recommended "Add file".

### SY-3 · When the storage can't be reached, Push opens a dead review whose only offered fix is "Reset local sync state"
- **Severity:** High
- **Where:** Project page → **Push** while the storage fails to open during preparation (offline, rejected R2/Dropbox credential, unreachable bucket)
- **Evidence:** `src-tauri/src/project_sync/service.rs:7698-7703` — a storage that fails to open yields `PushDestinationStatus::Unavailable { message: error.clone() }`, and `:7764-7767` copies the same error into `thread_comparison_error`. `src/components/project-sync/ProjectSync.tsx:1736-1740` gates only `requires_pull`, `remote_history_missing` and `remote_history_replaced`. `unavailable` therefore falls through and opens the review with the raw `threadComparisonError: context.thread_comparison_error` (:1815), never passed through `storageFailureMessage`. `src/components/project-sync/PushResourceWorkspace.tsx:733-739` shows the title "Conversations couldn't be compared, so nothing can be selected", the raw error as the message, and one action, "Reset local sync state"; the comment at :719-722 assumes stale metadata is "the usual cause". The reset confirm (`src/components/project-sync/ProjectSync.tsx:2555`) warns it "will remove all local session bindings for this project, including restored-session path mappings. It will also forget reviewed sync bases and Pull results."
- **Impact:** A network blip or an expired token becomes a Push review in which no conversation can be selected, showing transport error text and one button that erases this project's sync bases and session mappings. That is the wrong repair for a temporary outage, and its effects last: everything is re-reviewed and restored-session mappings are lost.
- **Fix:** In `openPushChooser`, handle `destination_status.state === "unavailable"` like the other gates. Don't open the review; raise the existing `action_failed` storage notice ("Push couldn't start") with `storageFailureMessage(...)` and its Retry / Reconnect button. Offer "Reset local sync state" only when `isIrrecoverableSyncError` recognises the comparison error.
- **Confidence:** confirmed from source. The path bar's own guard (`src/components/project-sync/ProjectLinksWorkspace.tsx:1244`, `workspaceStorageUnavailable = !!workspaceStorage && !workspaceStorage.available`) covers only a storage with no adapter in this build, not an offline or rejected one.

### SY-4 · A file with a scan warning is reported as "can't be captured — exclude it", when ticking "Mark reviewed" is the fix
- **Severity:** Medium
- **Where:** Push review of a non-Git project → a selected file flagged "Executable content" or "Credential-shaped content" (any shell script or key-shaped file)
- **Evidence:** `src/components/project-sync/PushResourceWorkspace.tsx:207-213` — an unacknowledged warning becomes a `kind: "local"` blocker (`state: "warning_unacknowledged"`). `:753-755` turns every local blocker into the footer line "`${localBlockingCount} selected item${…} can't be captured — exclude ${…} to push.`", and `:415-417` sets the Push title to "Exclude the items that can't be captured". The actual remedy is the card checkbox at `src/components/project-sync/ProjectFilesReviewPage.tsx:444-462` ("Mark reviewed"). The footer is not step-specific, so the sentence also shows on the Sessions step, where the file isn't visible.
- **Impact:** A user pushing a script is told the file cannot be captured and should be dropped. Following that instruction leaves the file behind without any error. The acknowledgement the safety rule requires is the one step the copy never mentions.
- **Fix:** Split the local blockers. For `warning_unacknowledged`, say "1 file has a warning — mark it reviewed in Project files, or exclude it", and make it a link that switches to the Project files step and scrolls to the first unreviewed card. Keep "can't be captured" for `unavailable` / `blocked` / `unknown` rows.
- **Confidence:** confirmed from source

### SY-5 · Push outcome counts only sessions — pushed files are never mentioned, and a push with no session rows reports every stored item as "sessions"
- **Severity:** Medium
- **Where:** Storage card outcome banner after any Push (project page)
- **Evidence:** `src/components/project-sync/syncOutcome.ts:112-114` — `const pushedCount = pushed.length > 0 || reported.length > 0 ? pushed.length : (result.resources_changed ?? 0);` and `:153` — `label: attention > 0 ? "pushed" : plural(pushedCount, "session")`. `src-tauri/src/project_sync/service.rs:10336-10345` — `resources_changed = Some(if was_published { results.len() } else { 0 })`, where `results` is every resource in the published manifest (`manifest.all_resources()`, which walks every scope: `crates/mallard-domain/src/lib.rs:4971-4975`), not what changed. `pushed` (`src/components/project-sync/syncOutcome.ts:100-104`) comes from conversation comparison entries only, so added or replaced project files and requirements never get a row or a stat. `:170-172` — `Pushed ${pushedCount} of ${pushedCount + attention} sessions` also counts comparison holds that were never selectable.
- **Impact:** A non-Git project that pushes three files sees "Push complete · 40 sessions" (the whole manifest). A mixed push never confirms that its files reached storage. The "of N" includes sessions the user never chose.
- **Fix:** Build the outcome from the reviewed selection by category ("3 sessions · 2 files"; files from the review's `pushProjectFileCommitImpact`). Take counts from the `results` states (`synced` vs `unchanged`) rather than the manifest size. Report holds as their own clause ("2 waiting for Pull").
- **Confidence:** confirmed from source

### SY-6 · A push limited by the size cap never says what was left out; it ends in a green "Push complete"
- **Severity:** Medium
- **Where:** Push review of a project whose unpushed sessions exceed the push limit → **Push** → storage card outcome
- **Evidence:** `src/components/project-sync/PushResourceWorkspace.tsx:283-294` — the recommended selection silently skips any session that no longer fits (`if (bytes > remainingBytes) continue;`). The review shows only the total (`:439` "This push · … of …") and per-row "Push size" chips (`src/components/project-sync/ProjectActivityPage.tsx:712-714`); no sentence says why older sessions are unticked. After the push, `src/components/project-sync/syncOutcome.ts:166-177` returns `tone: "success"`, `title: "Push complete"` and no action, because sessions outside the selection are never considered. The only remaining signal is the path-bar count badge (`src/components/project-sync/ProjectLinksWorkspace.tsx:2316-2318`). The push-budget specimen described otherwise: `src/push-budget-mockup.tsx:23-24` — "after the push: the outcome banner says how many didn't fit and offers Push again".
- **Impact:** A user with 60 sessions and a full limit pushes the newest 22 and is told "Push complete". On the second machine, 38 sessions are missing with no explanation.
- **Fix:** When the recommended selection drops sessions for size, say so above the list: "The 38 older sessions (1.2 GB) don't fit in this push — push again after it". Carry that count into the Push outcome in warning tone ("22 pushed · 38 didn't fit") with a "Push again" action.
- **Confidence:** confirmed from source

### SY-7 · After a partial failure, the outcome hides which rows failed and why behind hover, and offers no next step
- **Severity:** Medium
- **Where:** Storage card outcome banner after a Push with per-session failures ("Pushed 3 of 5 sessions"), or a Pull with failed actions ("2 changes need attention")
- **Evidence:** `src/components/project-sync/SyncOutcomeNotice.tsx:153-162` — each row's status ("Synced", "Held for Pull", "Failed") exists only as an icon with `data-tooltip`/`aria-label`. The failure text is behind an info glyph at `:163-171` (`data-tooltip={row.reason}`). `src/App.css:5939-5940` and `:6110-6111` reveal those tooltips only on `:hover` / `:focus-visible`. `src/components/project-sync/syncOutcome.ts:175-177` — a Push outcome offers an action only for held rows (`open_pull`); failed rows get none. Yet the line shown during the push, `src/components/project-sync/PushResourceWorkspace.tsx:1040`, promised "A running push finishes or fails whole — it can’t be cancelled midway." (The backend reports partial success: `src-tauri/src/project_sync/service.rs:10354-10358`, "Published revision {} — {} {} not pushed".)
- **Impact:** The user is told the push is all-or-nothing, then sees "Pushed 3 of 5" over a list of near-identical rows. Finding the two failures and their reasons means hovering each glyph, and nothing says to push again.
- **Fix:** Print the status word on failed and held rows, with the reason as a second line (`reason` is already on the row). Add a "Push again" action when `failed.length > 0`. Reword the in-flight line to "Can't be cancelled midway — any session that fails is listed afterwards."
- **Confidence:** confirmed from source

### SY-8 · Failed Pulls explain themselves with internal diagnostics, and "Reset local sync state" is offered by matching those strings
- **Severity:** Medium
- **Where:** Pull review error banner, or the failed row's info tooltip in the Pull outcome, when a reviewed conversation no longer matches at apply time
- **Evidence:** `src-tauri/src/project_sync/service.rs:10944` — `"conversation Pull action '{}' is stale at {:?}"` (an action id plus the Rust Debug name of an internal pin, e.g. `SemanticDigest`). `crates/mallard-infrastructure/src/pull_transcript.rs:72` — `"cloud conversation changed lineage or semantic content"`. The text reaches the screen verbatim in two ways. As a failed receipt (`src-tauri/src/project_sync/service.rs:12346-12351`) it becomes the row reason (`src/components/project-sync/syncOutcome.ts:257`, `reason: failure.message`). As a thrown error it becomes `` `Restore failed: ${errorMessage(reason)}` `` (`src/components/project-sync/pullReviewFlow.ts:108`), shown by `src/components/project-sync/RestorePlanView.tsx:368-372`. The repair button appears only when the prose contains those phrases (`src/components/project-sync/syncError.ts:9-11`: `"stale at semanticdigest"`, `"stale at lineagedigest"`, `"changed lineage or semantic content"`), wired at `src/components/project-sync/syncOutcome.ts:309-310` and `src/components/project-sync/RestorePlanView.tsx:373-379`.
- **Impact:** The customer reads "is stale at SemanticDigest" next to an opaque action id. The only way forward is a reset whose reason they cannot see, and any rewording of the backend text silently removes the button.
- **Fix:** Return a typed error code (e.g. `stale_review`, `lineage_changed`) with a customer sentence that says what changed ("This session changed in storage after you reviewed it") and why the offered action fixes it. Key `isIrrecoverableSyncError` on the code, not the prose. Keep the raw text in "Technical results".
- **Confidence:** confirmed from source. Needs runtime check: which surface (banner or outcome row) a given failure lands on.
