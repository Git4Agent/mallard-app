Link storage — four directions on "which destination?"

The shipped picker is a full-bleed band holding wrap-flow pills. With one available storage — the normal case, since everything already linked is filtered out — the band is ~95% empty, the pill carries no fact you could choose on, and the dismiss ✕ sits a screen-width away from it. Below: the band as it ships, then four directions. Switch the storage count first; n = 1 is the case that decides this.

What is wrong, by the book

Findings are against the shipped band at ProjectLinksWorkspace.tsx:3048–3080 and App.css:4842–4890. Two things it already gets right, and which every direction keeps: the trigger carries aria-expanded / aria-controls, and focus rings come from the app's own :focus-visible rules.

StandardWhat it asks forWhere the band fails
WCAG 2.1 1.3.1 Info and Relationships (A) Grouping conveyed visually is conveyed in the markup. A set of sibling <button>s in a bare <div>. Not a list, no group, no owner.
WCAG 2.1 2.4.6 Headings and Labels (AA) Groups get descriptive headings. "Choose a storage destination" is a <span>. Nothing labels the group; a screen reader reaches the pills with no context.
WCAG 2.1 2.4.3 Focus Order (A) Focus follows meaning when content appears and disappears. Opening does not move focus into the band; ✕ destroys the focused subtree with no return contract, dropping focus to <body>.
WCAG 2.1 2.5.8 Target Size, Minimum (AA) 24 × 24 CSS px. Pills are 36px tall — fine. The dismiss .sync-history-icon-action is fine too; its distance is the problem, not its size.
WAI-ARIA APG — Menu pattern A list of immediate commands is a menu hung off its trigger. A destination list rendered as free-floating pills matches no pattern; the app already ships the right one (.sync-path-menu.switcher).
Apple HIG (macOS) — Pop-up buttons Choosing one of a few appears near the control that opens it. The trigger is in the section head; the choices appear in a band at the card's foot, far below.
Nielsen #6 Recognition rather than recall Show what you need to choose with. The pill shows a name and a cloud. Two R2 buckets, or two Dropbox folders, are indistinguishable.
Nielsen #8 Aesthetic and minimalist design Every unit of screen competes with the rest. A full-width band for one 160px pill. The empty 1400px is the loudest thing on the page.
Fitts's law Pointer cost rises with distance. Choice at the left edge, dismiss at the right edge of the same 52px row — the two most likely next clicks are maximally far apart.

What is not wrong

The pills are not a broken listbox. Clicking links immediately and the act is reversible, so <ul> > <li> > <button> is the correct shape — APG's Listbox and Radio Group patterns are for select-then-submit, and adding a confirm step here would be friction on a reversible action. No direction below introduces one.

One hard constraint on the facts

A row may only carry what StorageSummary already holds: name, provider_label, icon, summary[], connection?, plus projectLinks for "already linked". The identifier line is summary[0], which is the provider's own first fact — Bucket for R2, Folder for Dropbox and local, Account for Managed Cloud. Nothing here scans, counts sessions, or reads sizes, per LandingPicker's house rule.

Note on the state column: connection is runtime-only and absent until this process has made a request to that storage, so on a cold launch most rows have no state at all. That is why none of the directions lean on it as the differentiator — it is a bonus column, and the identifier line does the real work.

A · Anchored menu The band is deleted. D · Modal dialog (recommended) A real <dialog> over a scrim: eyebrow + title + purpose line, B's rows in the body, Add storage and Cancel in the footer. .sync-modal / -header / -body / -footer, .sync-eyebrow, and B's row grammar — the sheet the repo chooser and the binding editor already use. Low-to-medium: one width rule (.sl-link-dialog), like .sync-binding-dialog's existing 720px. Grows well if linking ever asks a second question (which branch, which profile).
C · Card grid Same head as B, then one fixed-width card per destination in the Projects/Catalog landing grammar. .landing-picker-card and its title/location/detail parts. Highest. The grid must be re-capped (minmax(248px, 300px) + justify-content: start) — the shipped 1fr stretches a lone card across the full width and makes n=1 worse than Before. Weightiest treatment for the smallest decision. Best only if this list is expected to grow past ~6.

Appwise: does each direction fit what the app already does?

Checked against the shipped code, not against taste. The question that decides it is not CSS — it is which direction inherits a behaviour contract the app already keeps, and which one adds a fresh copy of it.

DirectionPrecedent in the appVerdict
A .sync-path-menu has exactly two consumers: SyncPathBar.tsx and StorageCatalogPage.tsx. The keyboard half is shared (menuKeyboard.ts) — but Escape, outside-click and focus-return are not: each consumer hand-rolls its own listener pair (SyncPathBar.tsx:433–454, StorageCatalogPage.tsx:977–997), down to the same copy-pasted comment. Compatible, but adds the third copy. A is the cheapest in CSS and the most expensive in behaviour code — unless the contract is first lifted into a shared hook, which is a refactor of two live surfaces, not a mockup. menuKeyboard.ts covers arrows only; it does not hand focus back, so A does not get 2.4.3 free.
B .sync-storage-index-row is the Storages index row — the same object (a storage) in the same shape. Nothing else in the app renders a transient chooser as an in-card band, though. Compatible. Right grammar for the object; the band itself has no precedent, so it invents one small pattern.
C .landing-picker-card is used by three landings — Projects, Catalog, Storages — each a full page where the card is the door to a destination. Mismatch. It borrows a page-level grammar for a transient in-card mode, so the picker reads as heavy as a landing page. Also the only direction that needs a shipped rule worked around (.landing-picker-grid's 1fr).
D BundleConnectionDialog.tsx:38–42 and ProjectBindingEditor.tsx:90–94 both open a native <dialog> with showModal(), carrying the same comment: supplies focus trap, Escape, inert. ProjectBindingEditor opens from this very page, from the same card head ("Set up project"). Strongest fit. Zero new contract code — the platform supplies what A would hand-roll. And the app already answers the neighbouring question, "which remote repo is this project?", with a modal list; answering "which storage?" the same way is the consistent move rather than a new one.

One thing D should not copy from BundleConnectionDialog: its role="radiogroup" + confirm button. That shape is right for an identity decision that must be committed. Linking a storage is one click and reversible, so D keeps one-click rows — the same reason none of the directions add a confirm step.

Implementation path, per direction

All four start by deleting the same thing: the picker block at ProjectLinksWorkspace.tsx:3048–3080 and the .storage-link-picker* rules at App.css:4842–4890 (the storage-link-reveal keyframe goes with them).

  • A — lift the Escape / outside-click / focus-return pair out of SyncPathBar and StorageCatalogPage into one hook beside menuKeyboard.ts and adopt it in all three call sites; mount the menu through TopLayer, because .project-storage-card is overflow: hidden and would clip it. New CSS: one width override.
  • B — add .sl-band*, .sl-rowbox, .sl-mark, .sl-state beside .sync-storage-index-row at App.css:4769. On open, focus the first row; on Cancel, hand focus back to the trigger — the one piece this direction must write itself.
  • C — as B, plus the --cols cap as a sibling class. Do not edit .landing-picker-grid in place: Projects, Catalog and Storages all depend on its 1fr behaviour.
  • D — a <StorageLinkDialog> modelled on BundleConnectionDialog: useRef<HTMLDialogElement> + showModal() on mount, .sync-modal header / body / footer, B's .sl-rowbox rows in the body. New CSS: one width rule next to .sync-binding-dialog at App.css:1508. Nothing else — Escape, focus trap, focus return and the inert backdrop come from the platform.

B's rows are the shared part: D is B's list inside the app's own sheet, so building B first and lifting it into a dialog later costs nothing twice. That is the cheapest hedge if the choice is not obvious.

Two behaviour changes, offered separately

Both are independent of A/B/C — take either with any direction. Toggle "Linked shown" above to see the first.

  • Show already-linked storages, inert. Today availableStorages filters them out, so the list shrinks as you link and at n=0 the picker cannot open at all. Showing them greyed with "Linked" answers Nielsen #6 and explains the shrinking list. The data is already in hand (projectLinks) — no new call.
  • Stop the label swap. The same button reads "Link storage" with candidates and "Add storage" without — one control, two verbs, decided by state the user cannot see. Put Add storage in the picker's own head (or the menu's footer, in A) and let the trigger keep one name, the way the Catalog and Storages landings already do.
