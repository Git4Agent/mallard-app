The rule, in order

  1. Read the link in Rust: open, one address, a page whose tail is exactly sessions/{id}, the id a cloud conversation resource id. Anything else under the repository stays the repository; a malformed id is not a link.
  2. Find the accounts on the host and ask the service for the repository, as a repository link does. The session is not asked for: the storage read that would confirm it is the Pull review's own.
  3. The project is here → the sheet names the repository, says it is one session of it, and offers Pull session…. Not here → Set up project…, as today.
  4. The verb opens the shipped Pull with a scope: one row, no files, nothing else compared. Synced → no review, the session's page. Not in the version → one sentence.
  5. Pull 1 applies the one action. The link's reviewed base and the cloud pin do not move; the row's own acceptance is recorded. The session's page opens.

Choices

1 · The link's form
  • A The session page's own address under open; the app decides.
  • B A second verb, mallard://pull?address=…: explicit on the wire, a second form to read and refuse-test, two links per page.
  • C A query flag on the page address, which the parser drops today.
2 · The website's button
  • Pull in Mallard: says what happens.
  • Open in Mallard: uniform with the repository page; the sheet's verb says Pull. (Toggle above.)
3 · Sheet or no sheet
  • Sheet first, as repository links: there is something to say (the account, the project, two accounts).
  • Straight to the review; the sheet only for the stops. (Toggle above.)
  • Sub-choice: the sheet names the repository and one session (recommended, no extra read) or reads the manifest for the title (layer 2).
4 · Where the scope lives
  • PullScope in Rust, as the session Push: plan and apply refuse anything outside the row; no base or pin moves.
  • The whole-project plan filtered in the window: compares every thread, enforces nothing, and would advance the base when nothing else is ticked.
5 · ?commit= on a historical view
  • Pull the current version; the button's tooltip says so.
  • Hide the button on historical views.
  • Honor the commit and pull that version (the planner reads the current snapshot only; a later layer).
6 · After Pull
  • Open the session's page.
  • Stay on the project's activity list with the row highlighted.
7 · Already here and up to date
  • No review: the session's page with one line.
  • Show the empty review.
8 · Project not on this computer
  • Set up project…, then the link again (the sheet says so).
  • Carry the session through setup and open its review when the project connects (layer 3).
9 · A non-Git project's files
  • The session alone; its page says the folder's files are still in Mallard Cloud.
  • The session Pull also shows the Files step, unticked (two scopes in one review, with the files' warning acknowledgements).
  • For a non-Git project set up from the link, the verb opens the project's first Pull with the session ticked.
10 · The item page's button
  • Pull in Mallard on a skill, plugin or pet page; the project repository page keeps Open in Mallard.
  • One label everywhere.
11 · After Add from a pull link
  • Open the item's Pull review on its page: the button said Pull, and the review is the second press.
  • Land as today, on the page with Pull 1, and leave the press to the person.
12 · The Catalog's scope
  • The window narrows the review and sends one choice, as the item's page does today.
  • Later: an only filter on the Catalog's prepare, so one item's Pull reads one repository.
