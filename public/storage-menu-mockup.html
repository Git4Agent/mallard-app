1 · The rulebook what was consulted, and what it forces

Nothing below is a preference. Each row is a published rule and the concrete constraint it puts on the six options.

SourceRuleConstraint here
W3C ARIA APG — Menu / Menu Button A menuitem is the only interactive thing in its row; menus use roving focus, arrows, Esc, type-ahead. Kills per-row buttons inside a menu (§7). If a popover needs real buttons in rows, it must stop being a menu — that boundary is what creates option F.
W3C ARIA APG — menuitemcheckbox / menuitemradio Menu state is a checked item with a stable label, not a verb that rewrites itself. “Switch to dark theme” becomes Dark theme ✓ in every option.
W3C ARIA APG — submenu pattern Cascades open on →/hover-intent, close on ←; a parent may also carry a default action. Makes option E legal; Windows menu conventions supply the click-parent-to-act default.
WCAG 2.2 — 1.4.11, 2.5.8, 2.4.13 3:1 state indicators; ≥24 px targets; focus visible and distinct from hover. Drawn checkmark in a reserved gutter; 32/44 px rows; outline-for-focus vs fill-for-hover in every option.
Apple HIG — Menus Trailing … for commands needing more input; destructive last, separated, styled; the same command may appear in two menus with identical wording. Ellipses everywhere; unlink always last in its group; the duplication clause is what legalises option B.
GNOME HIG — primary vs secondary menus One primary menu for app-scope items; object verbs live on the object's own control. The shape of option A: crumb menus own their objects, ⋯ keeps only Mallard.
Material 3 — Menus & overflow Overflow holds low-frequency commands of the surface's own scope, grouped by dividers; destructive uses the error role. Even the keep-it-right option (C) must regroup and rename — a flat 3-scope list fails Material on its own terms.
GitHub Primer — ActionList / ActionMenu Group headings name the group; danger variant sits in a terminal group; descriptions ride under labels. Headings split into label + right-aligned tally; scoped groups say This storage · <name>.
Chrome / Slack / GitHub switchers A switcher switches; managing the current item is a scoped section or a link to a management surface; they never put destructive controls on switch rows. Options A and D are the two halves of this precedent; F is what GitHub's repo switcher actually is (a dialog, not a menu).
NN/g — destructive actions & disabled controls Name the object being destroyed and its blast radius at the decision; prefer a disabled row with a reason to a vanishing one. “Unlink from HorrorGame…” + “Files stay on disk”; Link storage stays put at zero available and explains itself.
Fitts's law Acquisition cost grows with distance; put verbs near their nouns. The 604 px measurement in §0 is the score every option is judged against.

2 · Six options same rulebook, six placements

All six share the fixed anatomy of §4 — tick gutter, split headings, ellipses, danger and disabled conventions. They differ only in where the object verbs live and what kind of container holds them.

A · One home per scope scoped crumb menus, app-only ⋯

Recommended

Every menu answers for exactly one scope. The crumb that names an object carries that object's switcher and a band of its verbs, headed with the object's name; the ⋯ keeps only what has no crumb — Mallard itself. Storage and project get the same shape, so the pattern is learned once and read twice.

Why it leads. This is the Finder path bar / VS Code breadcrumb / GNOME shape: object verbs on the object, one primary menu for the app. Unlink lands beside its noun with its blast radius attached; the ⋯ drops from 10 rows to 2 and becomes honest about its scope. Cost: the one real trade-off of the whole page — users who learned “unlink is in the ⋯” must relearn once. The ⋯ shrinking to two rows is itself the signpost.

B · Both homes A's crumb menus, and the ⋯ keeps harmonized duplicates

Viable · redundancy

The crumb menus are exactly A's. The ⋯ additionally keeps a project band and a storage band — renamed, regrouped and object-headed so both homes say precisely the same thing. Apple's duplication clause allows this only with identical wording, icon and confirm in both places.

D · Lean switcher + management surface verbs live in the Library, one hop left

Viable · lean

The Chrome-profile / Slack-workspace answer: switchers switch, and a single Manage storage links… row deep-links to the Library, which shows every link at once with settings and unlink per row. The menu stays six rows forever, no matter how many storages exist — and the destructive verb lives on a page with room to explain itself.

Trade. Unlink is on the left but costs three clicks and a context switch; in exchange it is the only option that scales cleanly past three linked storages and can act on any link, not just the current one. The Library page already ships, so the surface exists. A quietly contains D — its ≥2-linked state adds the same row (§5).

E · Submenu per storage click a row to switch; its cascade holds the verbs

Viable · any-storage

The Windows cascade-with-default pattern: the row itself still switches on click, and its chevron (hover-intent, or →) opens a per-storage submenu. Uniquely among the menu options, verbs work on storages you are not currently on — unlink the team bucket without switching to it first.

storage crumb · submenu open on the second row
Storage2 linked
Team bucket
Trade. ARIA-legal (APG cascade + Windows default-item convention), and the only menu shape where every storage's verbs are one hover away. Costs: hover-intent timing is fiddly on a two-item cascade, the switch action gains an accidental-open hazard on slow mouse paths, a danger item is repeated into every submenu, and SyncPathBar has no submenu machinery today — the largest menu-code delta of A–E.

F · Switcher panel a small dialog, so rows may carry real controls

Strong alternative

The honest version of “put an unlink button on every row”: change the container, not the rule. GitHub's repo switcher and Slack's workspace switcher are not menus — they are small dialogs, where per-row buttons, footers and Tab are all legal. Each row switches; its ⋯ opens that storage's verbs; the footer holds link/add.

Why it's legal where §7's version isn't. The APG restriction — one control per row — applies to role="menu". This is role="dialog": rows are buttons in a list, the ⋯ is a second tab stop, WCAG's 24 px floor is met, and focus is trapped until Esc. Same pixels GitHub and Slack ship.
Costs. The heaviest build of the six: a new popover component beside SyncPathBar's menus (focus trap, restore, list nav), and the crumb stops matching the project crumb's menu behaviour — two popover grammars in one bar unless the project crumb converts too.

7 · Rejected outright not options — rule violations

Hover-revealed unlink button inside a menu row

rejected

Inside role="menu" a row may contain exactly one control — screen readers announce the nested button as part of the row's name or not at all. 20 px also misses WCAG 2.5.8's floor, hover-only reveal is keyboard-invisible, and it puts a destructive target inside the row you click to switch. Option F is this idea done legally — by changing the container's role, not by breaking the menu's.
